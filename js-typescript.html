Types are notes to your future self

TypeScript is JavaScript with one addition: you can write down what kind of value each thing is meant to be. The editor then checks your work as you type — catching a whole class of bugs before you even hit save.

Every .tsx file you've written already uses it. This guide names the parts you've been half-recognising, so they read as sentences instead of noise.

describe the shape once → the editor guards it everywhere
01

Why types

Plain JavaScript lets you make mistakes and only tells you at runtime. TypeScript tells you while you type.

In plain JS, nothing stops you calling user.nmae (a typo) or passing a number where a string belongs. You find out when it breaks — often deep in the running app. TypeScript reads your code before it runs and flags the mismatch right there in the editor, with a red underline.

◆ Analogy — a character sheet

As a novelist you might keep a sheet for each character: name (text), age (number), alive (yes/no). If a later chapter says the character's age is "purple", the sheet makes the mistake obvious at a glance. A TypeScript type is that sheet for your data — and the editor is the continuity checker that never gets tired.

02

The basic types

You annotate a value by adding a colon and a type. That's the whole syntax.

Code anatomy — a type annotation
const name: string = 'Pikachu'
Hover or tap a token · colon introduces the type · the value must match it
—
Each part explains its job.

The everyday types you'll use constantly:

basics.ts
const title: string   = 'Sharks'
const count: number   = 4
const loaded: boolean = true
const names: string[] = ['a', 'b']   // array of strings

// on a function: types for each parameter, and the return
function double(n: number): number {
  return n * 2
}
▲ Type inference — you don't always write it

TypeScript often infers the type from the value: write const n = 4 and it already knows n is a number — no annotation needed. You mostly write types on function parameters and data shapes, where it can't guess. Don't annotate everything; annotate what isn't obvious.

04

Interfaces

The payoff: describe the shape of a whole object once, then reuse that name everywhere.

Single types are handy, but the real power is describing an object's shape. An interface (or type) is a named character sheet for your data:

Code anatomy — an interface
interface Pokemon { name: string id: number nickname?: string }
Hover or tap a token · each line is one property: name and required type · ? means optional
—
Each part explains its job.

Now that name is a reusable type. Use it on a variable, a function parameter, an array — anywhere:

using-interface.ts
const pikachu: Pokemon = { name: 'Pikachu', id: 25 }

// a function that takes one Pokemon and returns a string
function label(p: Pokemon): string {
  return `#${p.id} ${p.name}`
}

// a whole list of them
const team: Pokemon[] = [pikachu]
◆ Why this matters for you

Once Pokemon is defined, the editor autocompletes p.name for you and red-flags p.nmae. If the API adds a field, you change the interface in one place and every component using it updates its safety net. This is the same idea as the data models in Vite & Data Models.

05

Types in your app

Where you actually meet TypeScript in the bootcamp — and one gotcha that bites everyone.

You've already hit types in a few places: typing an API response so the data has a known shape, typing a component's props, and the undefined guard in React Query where data might not have arrived yet.

typed-fetch.ts
// tell fetch's result what shape to expect
async function getPokemon(name: string): Promise<Pokemon> {
  const res = await fetch(`/api/pokemon/${name}`)
  return res.json()
}
✖ The any escape hatch defeats the point

When TypeScript nags, it's tempting to type something as any — which means "turn off checking for this". It silences the error but throws away every protection types give you. Reach for any only as a last resort. Usually the red underline is pointing at a real bug worth fixing, not a nuisance worth muting.

▲ Types vanish at runtime

TypeScript compiles down to plain JavaScript — all the type annotations are erased. They're a development-time safety net, not something that exists while your app runs. That's why a wrong type from an API (the data doesn't actually match your interface) won't be caught by TypeScript — it only checks the code you wrote, not the data the server sends. Scout the real shape in Postman first.

★

Recap

The essentials

  • A type describes a value's shape; the editor checks it before the code runs.
  • Annotate with a colon: name: string. Basics: string, number, boolean, string[].
  • TypeScript often infers types — annotate parameters and data shapes, not everything.
  • An interface names an object's shape; ? marks a property optional.
  • Reuse that name on variables, parameters, arrays, and function returns.

Watch out for

  • any switches off checking — avoid it; the error is usually a real bug.
  • Types are erased at runtime — they don't validate the data an API actually sends.
