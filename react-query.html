@tanstack/react-query · React + TypeScript

Fetching, without the plumbing

You already know how to fetch and juggle loading/error state by hand. React Query does that juggling for you — it's a cache with a request lifecycle. You describe what data you want by a key; it handles fetching, caching, deduping, and status, and hands your component { data, isPending, isError }.

This guide is concepts, not answers — enough to write your own useQuery calls for the Pokémon workshop, without me writing them for you.

queryKey + queryFn → { data, isPending, isError } the whole API surface you need to start.
01

Mental model

React Query manages a cache of server data, keyed by an identifier you choose. That's the whole thing — everything else follows.

With plain useState + useEffect, you own every step: a state for data, a state for loading, a state for errors, an effect to fetch, a dependency array, and cleanup so you don't set state on an unmounted component. Every fetch, repeated. Here's the same fetch, both ways:

✖ by hand — useState + useEffect
const [data, setData] = useState()
const [loading, setLoading] = useState(true)
const [error, setError] = useState()

useEffect(() => {
  fetchPokemon(name)
    .then(setData)
    .catch(setError)
    .finally(() => setLoading(false))
}, [name])
3 states · 1 effect · no caching · refetches every mount
✓ react-query — useQuery
const { data, isPending, isError } =
  useQuery({
    queryKey: ['pokemon', name],
    queryFn: () => fetchPokemon(name),
  })
1 call · cached by key · deduped · refetch built in

The difference isn't just fewer lines — it's the cache. React Query keeps a store of query results keyed by your queryKey. Mount a component that asks for ['pokemon', 'pikachu'] and it fetches; mount another asking for the same key while it's cached, and it reuses the result instead of refetching. Watch it happen — mount some components and observe the cache (right) and the network counter:

◆ Insight — the cache is the whole point

Notice that a second ['pokemon', 'pikachu'] didn't add a network request — it read the cached entry. That's what you're really buying: one source of truth for each piece of server data, shared across every component that asks for it, fetched once. The Devtools panel (which you'll add with <ReactQueryDevtools />) shows this exact cache live — get in the habit of watching it.

▲ "Cached" doesn't mean "never refetches"

By default a cached result is considered stale immediately, so react-query may refetch it in the background next time it's used (on a new mount, window refocus, reconnect) to keep it fresh — showing the cached data instantly meanwhile. You tune this with staleTime. For now, just hold two ideas: cached data appears instantly, and react-query keeps it fresh for you. You rarely manage that by hand.

02

Anatomy of useQuery

Two things go in — a key and a fetch function. A bundle of status comes out. That's the contract.

Code anatomy — a useQuery call
const { data, isPending, isError } = useQuery({ queryKey: ['pokemon', name], queryFn: () => fetchPokemonByName(name), })

Every part explains its own job.

The returned object has more than three fields — here are the ones you'll actually reach for:

the useQuery result
data       // the result — undefined until it resolves
isPending  // true: no data yet, first fetch in flight  (your spinner)
isError    // true: the queryFn threw
error      // the thrown error object (for the message)
isSuccess  // true: data is here and valid
isFetching // true during ANY fetch, incl. background refetch of cached data
◆ Insight — isPending vs isFetching

Two "is it loading?" flags, and the difference matters. isPending means no data at all yet — the very first load, when you show a spinner. isFetching is true during any request, including a background refetch when you already have cached data to show. So: spinner on isPending; a subtle "refreshing…" indicator (if you want one) on isFetching. For your workshop, isPending is the one you'll branch on.

03

Setup at the root

One QueryClient, one provider wrapping your app. Do it once; every useQuery below it just works.

For useQuery to have a cache to talk to, you create a QueryClient (the cache itself) and wrap your app in a QueryClientProvider. This is the same provider pattern as context — set up once at the root:

Code anatomy — main.tsx
const queryClient = new QueryClient() <QueryClientProvider client={queryClient}> <App /> <ReactQueryDevtools /> </QueryClientProvider>
Hover or tap a highlighted token above · one client · wrap once · add devtools
—
Every part explains its own job.
▲ Create the client outside your component

Make new QueryClient() a module-level constant (or a useState initialiser), not a plain variable inside a component body. If it's recreated on every render, you get a brand-new empty cache each time and lose all the benefits. Once, at the top, is the rule.

04

Common mistakes

Three that catch nearly everyone. Recognising them saves hours.

1 · Calling queryFn instead of passing it

This is the big one. queryFn wants a function it can call later — not the result of calling it now. Flip between the two and see what react-query actually receives:

what does queryFn receive?

2 · Using data before it exists

data is undefined until the query resolves. Reach into it too early — data.name on the first render — and you crash. In TypeScript you'll actually see this: the type of data is Pokemon | undefined until you narrow it.

guard first
// ✖ data is possibly undefined here — TS complains, runtime crashes
return <h2>{data.name}</h2>

// ✓ guard with isPending first — after this, data is defined
if (isPending) return <p>Loading…</p>
return <h2>{data.name}</h2>   // TS now knows data exists
✖ The guard is also a TypeScript narrowing

The if (isPending) return isn't just a nice loading UI — it narrows the type. Before it, data is Pokemon | undefined; after it, TypeScript knows the pending case already returned, so data is Pokemon. That's why the idiomatic order is guards first, success last: it satisfies both the runtime and the compiler in one move. Handle isError the same way, before the success return.

3 · Unstable or duplicate keys

The key is the cache identity. Two mistakes: keys that collide (different data, same key) and keys that miss a variable they depend on.

query keys
// ✖ every pokemon shares ONE cache entry — they'll clobber each other
queryKey: ['pokemon']

// ✓ the variable is part of the key — one entry per pokemon
queryKey: ['pokemon', name]

// ✓ same idea for your generation queries
queryKey: ['generation', generationId]
▲ Rule of thumb — if queryFn reads it, the key includes it

Any variable your queryFn uses to fetch should appear in the queryKey. If the fetch depends on name, the key needs name; otherwise react-query can't tell pikachu's data from ditto's, and switching name won't trigger a refetch. Keys are compared by value (deep equality), so inline arrays are fine — it's the contents that must be complete and stable, not the array's identity.

?Predict — how many requests?
// three components render at once:
useQuery({ queryKey: ['pokemon', 'pikachu'], queryFn: ... })
useQuery({ queryKey: ['pokemon', 'pikachu'], queryFn: ... })
useQuery({ queryKey: ['pokemon', 'ditto'],   queryFn: ... })
2 network requests
The two ['pokemon', 'pikachu'] queries share one cache entry, so react-query dedupes them into a single request. ['pokemon', 'ditto'] is a different key, so it fetches separately. Three components, two keys, two requests — the cache did the saving.
05

Loading & error patterns

The idiomatic shape: guard clauses in order — pending, then error, then the happy path.

The clean pattern is early returns, in this order. Each guard handles one state and bails, so by the time you reach the success render, both the runtime and TypeScript know data is there:

Code anatomy — the guard-clause pattern
const { data, isPending, isError, error } = useQuery({ /* ... */ }) if (isPending) return <Spinner /> if (isError) return <p>Error: {error.message}</p> return <Card pokemon={data} />
Hover or tap a highlighted token above · pending → error → success, in that order
—
Every part explains its own job.
◆ Insight — order is not arbitrary

Pending first, error second, success last — because each early return removes a possibility from what follows. After the isPending guard, data might exist but could have errored; after the isError guard, only success remains, so data is safe. Reordering these (success before the guards) is exactly how you hit the "data is undefined" crash from the last section. The pattern is the fix.

Try this yourself

Small experiments to run against your own Pokémon app. Nudges only — the code is yours to write.

How to use these

Each is a variation you can try in your workshop code and verify with the Devtools panel open. They build on each other. No solutions here — just enough of a push to find your own. Watch the cache panel as you go; it'll tell you whether you got it right.

A · Add a second query
// A component already fetches one pokemon. // Add a SECOND useQuery in the same component for its generation.
Shape
A component can call useQuery more than once — just call it a second time and destructure into differently-named variables (you can rename with { data: generation }). Two independent queries, two cache entries.
The key
Give the second query its own distinct key — something like ['generation', generationId]. Different kind of data → different key prefix. Check the Devtools: you should see two separate entries appear.
B · Make one query depend on another
// You only know the generationId AFTER the pokemon query resolves. // How do you stop the generation query running with undefined?
Concept
A query shouldn't fire until its inputs exist. React-query has an option that switches a query on or off based on a condition — look for one that takes a boolean and decides whether the query runs.
The option
It's enabled. Set enabled: !!pokemon (or whatever must exist first) on the dependent query. While it's false, the query waits — and stays isPending — until the condition flips true.
Watch for
Because a disabled query is still "pending", relying only on isPending can mislead you here. Look into isLoading vs isPending vs the fetchStatus for dependent queries — the Devtools will show you the difference in states as the condition flips.
C · Invalidate a query
// Force a refetch of a pokemon — e.g. after some action. queryClient.invalidateQueries({ queryKey: /* ? */ })
Reaching the client
You don't import the client into a component — you grab it with a hook: const queryClient = useQueryClient(). That gives you the same client from the provider.
What to pass
Pass the queryKey of what you want refetched: { queryKey: ['pokemon', name] }. Invalidating marks that entry stale and triggers a refetch. Try it with the invalidate button in the section-1 inspector — watch the network counter tick up and the entry refetch.
Prefixes
Keys are matched by prefix. Invalidating { queryKey: ['pokemon'] } (no name) invalidates every pokemon query at once — that's why the string label at the front of the key is useful. Try invalidating a whole group vs a single entry and compare.
★

Recap

Mental model

  • React Query is a cache with a request lifecycle — it replaces the useState/useEffect fetch dance.
  • Data is stored by queryKey; same key = same cache entry, shared & deduped across components.
  • Cached data shows instantly; react-query refetches in the background to keep it fresh (see staleTime).

useQuery

  • Takes one object: queryKey (array id) + queryFn (function returning a promise).
  • queryFn must be a reference: () => fetchPokemonByName(name), not fetchPokemonByName(name).
  • Returns { data, isPending, isError, error, isSuccess, isFetching } — take what you need.
  • isPending = no data yet (spinner). isFetching = any fetch, incl. background.
  • Setup once: new QueryClient() + <QueryClientProvider client={...}> at the root, plus Devtools.

Pitfalls & patterns

  • Guard before using data — data is undefined until it resolves (TS: T | undefined).
  • Idiomatic order: if (isPending) → if (isError) → success. The guards narrow the type too.
  • Keys include their variables — ['pokemon', name], not ['pokemon']. Compared by value.
  • Create QueryClient outside components so the cache survives renders.
  • Dependent queries: enabled. Refetch on demand: queryClient.invalidateQueries({ queryKey }) (matches by prefix).
