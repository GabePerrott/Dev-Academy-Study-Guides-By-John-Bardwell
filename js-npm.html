Unit 1 · T4 — Learning & NPM

Standing on code you didn't write

Up to now you've written every line yourself. npm is where that changes: it lets you pull in building blocks other people already built and battle-tested — and package.json is the file that keeps track of it all.

This one's less about running JavaScript and more about the tooling around it. So the interactives are a clickable package.json, a version bumper, and hover-anatomy on the terminal commands and import lines.

$ npm install the command you'll type more than any other by the end of bootcamp.
01

What npm actually is

Node Package Manager. Think of it as an app store for code — except everything's free and you install it into your project.

A package is a bundle of code someone else wrote and published so you don't have to. npm is the tool that fetches those packages and drops them into your project, and npmjs.com is the registry where they all live. It's relied on by well over 17 million developers — so when you install something, you're plugging into an enormous shared toolbox.

◆ Insight — why this is a big deal

The whole modern web is built this way. Nobody writes a date-formatter, a test runner, or a UI framework from scratch anymore — they install one. Your job as a developer is increasingly about choosing and wiring together good packages, not reinventing them. That's not cheating; it's the actual skill. The react package you'll use later? 27 million downloads a week. You'll be standing on all of that.

Two kinds of "importing" now exist side by side, and it's worth keeping them straight:

Your own code

Local modules

Files you wrote, imported by a relative path: import x from './lib.js'. This is the import/export from the T3 modules guide.

Other people's code

Installed packages

Code you pulled from npm, imported by bare name: import cowsay from 'cowsay'. No ./ — that's the tell.

02

package.json

The instruction manual for your project. Every Node project has one — it's the first thing you set up.

It's a configuration file holding your project's metadata, its list of packages, and its scripts. If a project doesn't have one, you create it by running npm init and answering the prompts (or npm init -y to accept every default at once).

Hover any part of this real package.json to see what that line is for. The one that matters most is highlighted differently — see if you can guess which before reading it.

Interactive package.json — hover any field
{ "name": "cowsay-demo", "version": "1.0.0", "description": "", "main": "index.js", "type": "module", "scripts": { "test": "vitest", "count-deps": "ls node_modules | wc -l" }, "dependencies": { "cowsay": "^1.6.0" }, "devDependencies": { "vitest": "^1.6.0" } }

▲ The line everyone forgets — "type": "module"

Straight after npm init, add "type": "module". This is what lets you use import/export (the ESM syntax from T3). Leave it out and Node falls back to the old CommonJS style, and your import lines throw errors that don't obviously point at the cause. When an import mysteriously won't work in a new project, this missing line is the first thing to check.

When it finishes, a few things have appeared. Here's roughly what you'd see:

zsh — cowsay-demo
$ npm install cowsay
added 24 packages in 2s

$ ls
index.js   node_modules   package.json   package-lock.json

dependencies vs devDependencies

The -D flag decides which bucket a package lands in, and the distinction is genuinely useful:

dependencies

Needed to run

npm install cowsay. Anyone actually using your app needs these. They're part of the finished product.

devDependencies

Needed only to build/test

npm install -D vitest. Test runners, build tools. Useful to you while developing, invisible to end users.

node_modules and package-lock.json

Two things get created for you on first install:

◆ Insight — node_modules is huge, and that's fine

node_modules is the folder every package (and every package's packages) gets downloaded into. It gets enormous fast — installing one small thing can pull in dozens of others. There's a running joke that node_modules is the heaviest object in the universe. The reassuring part: it's completely disposable. Delete it and npm install rebuilds it exactly from your package.json. You never edit it by hand, and you never commit it to git (more on that in section 7).

◆ Insight — package-lock.json = reproducibility

package-lock.json is an auto-generated file recording the exact version of every package that got installed, all the way down. package.json might say "cowsay ^1.6.0" (a range), but the lock file pins the precise version everyone ends up with — so your machine, your pair partner's machine, and the marker's machine all install identical code. Unlike node_modules, you do commit the lock file. You don't need to read or understand its contents; just know it's there doing that job.

04

Using a package

Installed code is just a module. You bring it in with the same import syntax you already know.

Package docs sometimes still show the old CommonJS way — const cowsay = require('cowsay'). Because we set "type": "module", we use the modern ESM import instead. Same idea, newer syntax:

Code anatomy — importing an installed package
import cowsay from 'cowsay'
Hover or tap a highlighted token above · the missing ./ is what makes it a package import
—
Every part explains its own job.
✖ The one that confuses everyone — bare name vs ./path

This is the single most important distinction between T3 imports and T4 imports:

from './lib.js' — the ./ means "a file I wrote, right here next to this one."

from 'cowsay' — no ./ means "a package, go find it in node_modules."

Node uses that leading ./ (or its absence) to decide where to look. Get them mixed up and you'll see "cannot find module" — usually because you either added a ./ to a package name or forgot it on your own file.

Once imported, you use it however its README says. cowsay prints a talking cow, and its properties let you customise it — the eyes, the tongue, and so on:

node — index.js
$ node index.js
 _____________
< I'm a module >
 -------------
        \   ^__^
         \  (oo)\_______
            (__)\       )\/\
                ||----w |
                ||     ||

Node runs a .js file with node <filename> — the same way you'd run any script from the terminal.

Semantic versioning

Those three numbers on every package — like 19.1.0 — aren't random. Each one tells you how risky an update is.

Bump a number to see what it means for people relying on this package.
◆ What each bump means

Major (the left number) → something changed so much it might break code using the old version. Upgrading may mean fixing your own code. This is the one to watch.

Minor (middle) → new features added, but backwards-compatible. Safe to upgrade; you just gain options.

Patch (right) → small fixes, usually bugs. Safe, nothing new to learn.

▲ Connecting it back — that ^ in package.json

Remember "cowsay": "^1.6.0"? The caret ^ uses exactly these rules: it says "let this update to new minor and patch versions automatically, but never jump to a new major without me deciding." It's a safety setting — you get bug fixes and features for free, but the potentially-breaking major upgrades stay a manual choice. You don't need to memorise the symbols yet; just know the caret is quietly protecting you from surprise breakage.

06

Scripts

Nicknames for terminal commands, saved in package.json so you (and your team) don't have to remember the long version.

A script is just a saved terminal command with a short name. You run it with npm run <name>. The exceptions are test and start — for those two, run is optional, so npm test and npm start work directly. That's why you've been typing npm test since foundations without thinking about it.

zsh — cowsay-demo
$ npm run count-deps
> cowsay-demo@1.0.0 count-deps
> ls node_modules | wc -l

      69
?Read the script
"count-deps": "ls node_modules | wc -l"

What is this script actually doing? Think it through, then reveal.

ls node_modules → list everything in the folder
| → pipe that list into the next command
wc -l → count the lines
So it lists every item inside node_modules and counts the lines, giving a rough tally of how many packages are installed. The | ("pipe") feeds the output of the left command into the right one. It's not something you'll need often — it's a fun way to see scripts in action and to appreciate just how much gets pulled in by a couple of installs.
◆ Insight — the one you'll live in: dev

The count-deps script is a toy, but scripts themselves are central. The moment you start building websites you'll be running npm run dev constantly — it starts a local server so you can see your site in the browser and have it reload as you edit. Get comfortable with the npm run <name> pattern now; it's about to become muscle memory.

07

.gitignore

A list of files git should pretend it can't see. Top of the list, always: node_modules.

When you commit a project, you don't want to push node_modules to GitHub — it's huge, it's downloaded from the internet anyway, and anyone who clones your project can regenerate it with a single npm install. So you tell git to ignore it by listing it in a .gitignore file at the root of your project.

.gitignore
node_modules
.DS_Store
*.log

Once node_modules is in there, you'll see it go greyed-out in VS Code — git is no longer tracking it. The .DS_Store line is a macOS housekeeping file that sneaks into repos if you've opened the folder in Finder; ignoring it keeps your commits clean.

◆ Insight — the mental rule for what to ignore

The pattern behind .gitignore: don't track anything that's generated, downloaded, or machine-specific. node_modules is downloadable (from package.json), .DS_Store is machine-specific junk, log files are generated. The things you do commit are the irreplaceable ones — your source code, your package.json, and your package-lock.json. If it can be rebuilt automatically, git doesn't need it.

Recap & cheat sheet

The whole unit, plus the commands you'll actually type.

Concepts

  • npm = Node Package Manager. Installs packages (other people's code) from npmjs.com.
  • package.json = your project's instruction manual: metadata, packages, scripts.
  • "type": "module" — add it after npm init so import/export (ESM) works.
  • dependencies = needed to run · devDependencies = needed only to develop (-D flag).
  • node_modules = downloaded packages. Huge, disposable, never committed.
  • package-lock.json = exact versions for reproducible installs. Do commit it.
  • Import your files with './path'; import packages by bare name (no ./).
  • Versions = major.minor.patch. Major = breaking, minor = new feature, patch = bug fix.
  • .gitignore = don't track generated/downloaded/machine-specific files. node_modules first.

Commands

  • npm init — create a package.json (add -y to accept defaults)
  • npm install <pkg> — add a runtime dependency
  • npm install -D <pkg> — add a dev-only dependency
  • npm install — rebuild node_modules from package.json (e.g. after cloning)
  • npm run <name> — run a script · npm test / npm start need no "run"
  • node <file> — run a JavaScript file
