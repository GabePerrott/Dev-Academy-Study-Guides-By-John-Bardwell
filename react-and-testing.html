Unit 2 · T02 — React & Testing React

Build UI from components, then prove it works

You're entering React — the library that builds interfaces out of small, reusable pieces that redraw themselves whenever your data changes. This guide covers React from the ground up, then turns to testing it: how you write code that checks your components render what you meant.

Two live tools do the heavy lifting — a re-render visualiser for the core React idea, and a real test runner you can fire at a mini app and watch pass or fail.

UI = f(state) the whole of React in three symbols. We'll unpack it.
Part A

React

Components, JSX, props, state — everything you need before testing makes sense.

01

The mental model

React builds your page out of components, and redraws them automatically when their data changes. That's the core.

Before any syntax, hold two ideas. First: a React app is built from components — self-contained pieces of UI (a header, a button, a greeting card) that you combine like building blocks, and reuse. Second, and the one that makes React React:

◆ The one idea — UI = f(state)

Your interface is a function of your data. You don't manually reach into the page and change text when something happens (that's the old, "imperative" way). Instead you describe what the UI should look like for any given data, and when the data changes, React re-runs your component and updates the screen for you. You write the what; React handles the how. This is called being declarative.

Think of a component as a stamp that prints UI from data. Same stamp, different data in → different UI out. Change the data, and React re-stamps. Everything below is detail on top of that.

02

Components & JSX

A component is a function that returns markup. That markup is written in JSX — HTML-like syntax living inside JavaScript.

A component is just a function whose name starts with a capital letter and which returns what to show. Here's the smallest real one:

Code anatomy — a component
function Greeting() { return <h1>Kia ora!</h1> }
Hover or tap a highlighted token above · a component in, UI out
—
Every part explains its own job.

You then use it like a tag: <Greeting />. That "HTML inside JavaScript" is JSX, and it has a few rules that trip everyone up at first:

One root element

A component must return one top-level element. Wrap siblings in a <div> or an empty <>…</> fragment.

className, not class

class is a reserved word in JS, so JSX uses className for CSS classes.

{ } drops in JavaScript

Curly braces embed a JS expression: <h1>Hi {name}!</h1>. Anything that produces a value works.

Close every tag

Even lone tags self-close: <img />, <br />. JSX is stricter than HTML here.

▲ JSX is not HTML wearing a costume

It looks identical, but JSX compiles down to function calls that build a description of your UI. That's why the rules feel fussy — you're really writing JavaScript. The { } braces are the seam where you drop back into plain JS: a variable, a bit of math, a .map(). Whenever you want dynamic content in your markup, you reach for braces.

03

Props

Props pass data into a component from its parent — the inputs that let one component render many ways.

A component that always says the same thing isn't much use. Props (short for properties) are the data you pass in, exactly like attributes on an HTML tag. They're what make a component reusable — same stamp, different ink:

Code anatomy — props in, and passing them
function Greeting({ name }) { return <h1>Hi {name}!</h1> } // used as: <Greeting name='Aroha' />
Hover or tap a highlighted token above · parent hands data down to child
—
Every part explains its own job.
✖ Props are read-only

A component must never change its own props — they belong to the parent that passed them. Think of them as arguments to a function: you receive them, you use them, you don't reassign them. If a component needs data that changes over time in response to what the user does, that's not props — that's state, which is next, and which is the actual heart of React.

?Predict what renders
function Hi({ name }) {
  return <p>Hi {name}!</p>
}

// rendered as:
<Hi name="Wiremu" />
Hi Wiremu!
The name prop arrives as "Wiremu", the braces drop it into the paragraph, and the component renders that one line. Pass a different name and the same component renders differently — that's the whole point of props.
04

State & re-rendering

State is data a component owns and can change. When it changes, React re-runs the component and updates the screen. This is UI = f(state) in motion.

State is memory that lives inside a component and can change over time — a counter's count, whether a menu is open, text in an input. You create it with the useState hook:

Code anatomy — useState
const [count, setCount] = useState(0) // to update: setCount(count + 1)
Hover or tap a highlighted token above · value + setter, always a pair
—
Every part explains its own job.

The magic is in that setter. Calling setCount doesn't just change a number — it tells React to re-render: re-run the component with the new value and update the screen. Watch it happen. Click the button and see each state change trigger a fresh render:

Click the button. Each click updates state, and React re-runs the component to match — that's a re-render.
◆ Insight — why not just change the variable?

You might wonder why you can't write count = count + 1. Because React wouldn't know anything changed — nothing would tell it to update the screen. The setter is the signal. State and re-rendering are two halves of one mechanism: state changes cause re-renders, and re-renders reflect state. That loop is why a React UI stays in sync with its data without you touching the page directly.

05

Dynamic UI

Three everyday patterns: rendering a list from an array, responding to events, and showing things conditionally.

Lists with .map()

To render many items you .map() an array into an array of JSX — the same .map() from the arrays guide, now producing markup:

Greetings.jsx
const people = ['Sina', 'Wiremu', 'Aroha']

return (
  <div>
    {people.map((name) => (
      <h1 key={name}>Hi {name}!</h1>
    ))}
  </div>
)
// renders three headings: Hi Sina!  Hi Wiremu!  Hi Aroha!
▲ The key prop — don't skip it

Each mapped element needs a unique key prop. React uses it to tell list items apart when the data changes, so it can update efficiently instead of redrawing everything. Leave it out and React warns you. Use something stable and unique — an id if you have one, not the array index if the list can reorder.

Events

You respond to user actions with event props like onClick — camelCased, and you hand them a function to run:

Button.jsx
<button onClick={() => setCount(count + 1)}>
  Clicked {count} times
</button>
// note: onClick={fn} — you pass the function, you don't call it

Conditional rendering

Show something only sometimes, using plain JS inside braces — a ternary, or && for show-or-nothing:

Status.jsx
{isLoggedIn ? <p>Welcome back</p> : <p>Please log in</p>}

{hasError && <p>Something went wrong</p>}
// &&: render the right side only when the left is true

That's the working core of React. With components, props, state, lists, events and conditionals, you can build real interfaces — and now you have enough to understand what it means to test them.

Part B

Testing React

Writing code that renders a component in a fake browser and checks it shows what you meant.

06

The testing mindset

Same Arrange / Act / Assert you know — but now you assert on the DOM: what's on the screen, not what a number equals.

You've written tests before with Arrange, Act, Assert. The shape carries over; what changes is what you're checking. With React you're testing the front end — what actually renders — so:

Arrange

Render the component into a pretend browser. You're setting the stage — putting the component on a fake screen.

Act

Do the thing you're testing — click, type. Often nothing yet for simple "does it render?" tests.

Assert

Observe the DOM: is this heading visible? does the image have the right alt text? Checking the screen, not arithmetic.

◆ Insight — the shift from "3 + 3 === 6"

Earlier tests asked "does this logic produce the right value?" React tests ask "does the right thing appear on screen, and is it accessible?" The assertion targets an element in the page — its text, its attributes, whether it exists at all. You no longer have to write Arrange/Act/Assert as comments, but keeping the three beats in mind keeps tests readable.

07

Setup: library & jsdom

Two tools make React testable: Testing Library (renders & queries components) and jsdom (a fake DOM). You set this up once — and you don't memorise it.

Two pieces of vocabulary you'll meet immediately:

Testing Library (React)

Gives you render and screen. It renders a component and lets you query it the way a user would — by visible text, by role — which also nudges you toward accessible markup.

jsdom

A fake DOM in memory. Tests don't open a real browser — jsdom builds a pretend one so your component has somewhere to render. Nothing appears on screen when tests run.

We run tests with Vitest (the Vite-native equivalent of the older Jest). To make Testing Library's DOM matchers work with Vitest, a project needs a bit of one-time wiring in a setup file. You don't memorise this — it lives in code-for-class to copy when starting a fresh project. But one line is special:

Code anatomy — the special comment at the top of a test file
// @vitest-environment jsdom import { render, screen } from '@testing-library/react' import { describe, it, expect } from 'vitest'
Hover or tap a highlighted token above · the one comment that isn't ignored
—
Every part explains its own job.
✖ The comment that breaks everything if missing

We spend all of Foundations learning that comments are ignored — so this one feels wrong. But // @vitest-environment jsdom is a directive Vitest deliberately reads. Forget it and you'll get confusing errors about document not existing, because there's no fake DOM to render into. When a React test mysteriously can't find the page, check this line is at the very top first.

The other setup wiring, briefly, so you recognise it: a beforeEach(cleanup) that wipes the fake DOM before every test (so tests don't bleed into each other), and an expect.extend(matchers) that adds the DOM-aware checks like toBeVisible. Copy it once; move on.

08

Queries & the screen

render puts the component in the fake DOM; screen finds elements in it. Getting the right query is most of the skill.

You render(<App />), then reach for elements through screen. The query name encodes two choices: how many you expect, and what to match on.

QueryWhen to use it
getByRoleOne element of a role. Roles come from semantic tags: an <h1> is role heading, an <img> is role img.
getAllByRoleMany of a role — returns an array. Use when the page has several headings and you want them all.
getByTextFind by visible text. Good for things with no obvious role, like a <p> tagline.
getByAltTextFind an image by its alt text — the accessible description.
findBy… / findAllBy…The async versions. Same queries, but they wait for the element to appear. More on why next section.

A role query can be narrowed — getAllByRole('heading', { level: 2 }) grabs only <h2>s. Now try it for real. Below is a live mini "greetings app" rendered into this page, and real tests you can run against it. Hit Run and watch each pass or fail:

09

Async & matchers

Why findBy needs await, and the handful of matchers you'll use to assert on the DOM — including regex for flexible text.

Why async / await

Grabbing something from the fake screen can take a beat — a millisecond longer than the test itself. The findBy queries return a promise for that reason, so you await them, and mark the test async:

async-query
it('renders a heading', async () => {
  render(<App />)
  const headings = await screen.findAllByRole('heading')
  expect(headings[1]).toHaveTextContent('Hi Sina!')
})
// async + await: wait for the query before asserting
◆ Insight — array indexing comes back

Note headings[1] — the queries hand you a normal array, so everything from the arrays guide applies: [0] is the first, [1] the second. The same off-by-one care you practised in the katas is exactly what you need when you grab "the second heading" from a list of results.

The matchers

Matchers are the DOM-aware checks chained after expect(...). The ones you'll reach for most:

MatcherChecks that…
toBeInTheDocument()the element exists in the DOM at all.
toBeVisible()the element is actually visible on the page (not hidden).
toHaveTextContent(text)the element contains that text. Accepts a string or a regex.
toHaveAttribute(name, value)the element has an attribute — e.g. an <img> has the right src.
toHaveAccessibleName()the element has an accessible name (alt text, a heading label) for screen readers.

Regex for flexible text

Sometimes you only care that a word is present, not the whole exact string. A regex between slashes does that, and i makes it case-insensitive:

regex-match
// exact string — must match all of it:
expect(heading).toHaveTextContent('Greetings to everyone')

// regex — just needs to CONTAIN 'greetings', any case:
expect(heading).toHaveTextContent(/greetings/i)
▲ The /i flag, plainly

/greetings/i means "the letters g-r-e-e-t-i-n-g-s appear somewhere, and don't care about capitals." Without i, Greetings wouldn't match greetings. Regex matching is looser and often what you want for user-facing copy that might get reworded slightly — you assert the important word is there rather than pinning the exact sentence.

10

Break your tests + accessibility

A passing test you've never seen fail might be lying. And good, accessible markup is what makes components testable in the first place.

Always break a passing test

In the demo, a test passed — then the presenter changed the expected text and it still passed for a moment, because of a subtle mistake. Only by deliberately breaking it did the real failure show up. The habit: when a test passes on the first try, change something so it should fail, and confirm it does. Then put it back.

✖ Why a green test can still be wrong

A test that passes no matter what isn't testing anything — maybe it's querying the wrong element, or the assertion is weaker than you think. Watching it fail when it should proves it's actually wired to the thing you care about. A test you've never seen go red is a test you can't fully trust. Try it in the runner above: edit the expected tagline text and re-run — watch it turn red, which is the proof it's real.

Accessible markup makes testable markup

Testing Library queries by role and by alt text on purpose — it wants you to build pages that screen readers can navigate. That means the same choices help users and make your tests natural to write:

Semantic tags

Use an <h3> for a heading, not a styled <span>. The tag carries meaning: role "heading", level 3. That's what getByRole finds.

Alt text on images

Non-decorative images need a short, descriptive alt. It's what a screen reader announces — and what getByAltText queries.

Keep alt short

Descriptive like a tweet. Don't write "image of…" — the <img> tag already says it's an image. Decorative images can have empty alt.

◆ Insight — accessibility and testability are the same discipline

This is the quiet lesson of the whole unit. When you reach for a real heading tag instead of a styled span, and give your images honest alt text, you're helping people who use screen readers and giving your tests a stable, meaningful handle to grab. Testing Library was designed this way on purpose: the tests get easier precisely when the markup gets kinder. Good markup pays double.

Recap

React

  • UI = f(state) — describe what the UI should be for given data; React redraws when data changes (declarative).
  • A component = a capitalised function returning JSX (HTML-like syntax in JS).
  • JSX rules: one root element, className not class, { } drops in JS, self-close every tag.
  • Props = data passed in from the parent. Read-only — never change your own props.
  • State = useState(initial) → [value, setter]. The setter updates value AND triggers a re-render.
  • Lists: .map() array → JSX, each item needs a unique key.
  • Events onClick={fn} (pass, don't call) · conditionals with ternary or &&.

Testing React

  • Still Arrange / Act / Assert — but assert on the DOM, not arithmetic.
  • Testing Library gives render + screen; jsdom is the fake DOM; Vitest runs it.
  • // @vitest-environment jsdom — the one comment Vitest reads; forget it and DOM tests break.
  • Queries: getByRole / getAllByRole (heading, img), getByText, getByAltText.
  • findBy… are async — await them, mark the test async.
  • Matchers: toBeInTheDocument, toBeVisible, toHaveTextContent, toHaveAttribute, toHaveAccessibleName.
  • /word/i = contains that word, case-insensitive.
  • Always break a passing test once, to prove it's real.
  • Semantic tags + alt text = accessible and testable. Same discipline.
