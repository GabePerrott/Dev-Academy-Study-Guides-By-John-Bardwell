Unit 2 · T06 — Client-Side Routing

One page that behaves like many

So far your React apps live on a single page — you click a button and code manually swaps the content. Client-side routing lets the URL do that instead: type /pumpkins, see the pumpkins page. Real web addresses you can bookmark and share, with no page reload.

This builds straight on the React guide. If components, props and state feel shaky, that one comes first — routing just decides which component shows.

URL → component the whole job of a router, in three characters.
01

The problem it solves

A single-page app has no real addresses. Routing gives it URLs — so pages can be typed, bookmarked, and shared.

Up to now, a React app has been one page. When you clicked "Fun with Numbers", some state changed and the app swapped in that component. It worked — but the address bar never changed. You couldn't type a URL to jump straight to a page, and you couldn't send a friend a link to it. Everything was /.

Most of the web doesn't work like that. On TradeMe, trademe.co.nz/about takes you straight to the about page. You can bookmark it, share it, hit back. Client-side routing gives your React app that same power — while staying a single-page app under the hood.

✖ Before — state decides

A variable like activeCarter tracks what to show. Click a button → change the variable → different component appears. URL stays /. Nothing to bookmark.

✓ After — the URL decides

The address bar drives what shows. /numbers → Fun with Numbers. Type it, bookmark it, share it. The router reads the URL and picks the component.

◆ Insight — still one page, and that's the trick

This is the part that surprises people: your app never actually loads a second page. React Router fakes multiple pages by watching the URL and swapping components in and out. That's why clicking links feels instant with no loading spinner — nothing is being fetched or reloaded. It's how Facebook, Instagram and most modern sites feel so snappy: one page, many URLs, zero reloads.

03

Setting up routes

You list your pages and their addresses in a routes.tsx file, then hand that to a RouterProvider in index.tsx.

The setup has two files. First, routes.tsx — a list matching each path to the component that should show there. You'll write this once per project (most challenges give it to you already):

Code anatomy — routes.tsx
const router = createBrowserRouter(createRoutesFromElements( <Route path='/' element={<Home />} /> <Route path='/about' element={<About />} /> )) export default router
Hover or tap a highlighted token above · each Route = one path + one component
—
Every part explains its own job.

Then in index.tsx, instead of rendering <App /> directly, you render a RouterProvider and hand it that router. This is the switch from "one fixed app" to "whatever the URL says":

index.tsx
// old way — always the same component:
// root.render(<App />)

// routed way — the URL decides what shows:
import { RouterProvider } from 'react-router-dom'
import router from './routes'

root.render(<RouterProvider router={router} />)
▲ You set this up once — don't sweat memorising it

The exact import names (createBrowserRouter, createRoutesFromElements) are fiddly and you're not expected to recall them cold. Most challenges hand you this scaffolding already built. What matters conceptually: a list of path→component pairs, wrapped up and handed to a provider that watches the URL. Copy the setup, then spend your energy on the routes themselves.

04

Links, not anchors

The plain HTML anchor tag reloads the whole app. React Router's Link navigates without a reload — so you keep your state.

You already know the anchor tag from Foundations: <a href="/about">. It still works in React — but it does something you don't want. Clicking an anchor forces a full page reload, which throws away all your app's state and shows a loading flash. That kills the whole single-page-app advantage.

Instead, React Router gives you a <Link> component. It looks and behaves like an anchor, but navigates within your app — no reload, state preserved. The one difference in code: it uses a to prop instead of href:

Code anatomy — Link vs anchor
// ✖ <a href='/about'>About</a> <Link to='/about'>About</Link>
Hover or tap a highlighted token above · to replaces href, no reload
—
Every part explains its own job.
✖ The takeaway, blunt version

Do not use anchor tags for navigating your app. Use <Link>. An anchor reloads and wipes state; a Link glides. This is one of those rules that's easy to slip on because <a> is such muscle memory from Foundations — so when a click mysteriously resets your app, an stray anchor tag is the first thing to check.

05

Dynamic params

One route can serve endless pages. A colon in the path marks a slot that changes — the product id, the username — read back with useParams.

Imagine a shop with thousands of products. You don't write a route for each one. You write one route with a changeable slot, marked by a colon:

routes.tsx
<Route path='/products/:id' element={<Product />} />
//              ^^^ the colon makes :id a DYNAMIC slot
// /products/1  → id is "1"
// /products/99 → id is "99"   ...same component, different data

The :id is a parameter — a placeholder that takes on whatever the user typed. Inside the component, you read it with the useParams hook:

Code anatomy — useParams
const { id } = useParams() if (!id) return <p>Missing product ID</p> return <h1>Product {id}</h1>
Hover or tap a highlighted token above · route names the slot, useParams reads it

▲ Params always come in as strings

Notice the value is "42" with quotes, not 42. Everything from a URL is text — so if you need to do maths or look something up by numeric id, you may need to convert it with Number(id). A classic early bug: comparing the string "42" to a number 42 and wondering why it never matches. Same string-vs-number care from the earlier guides.

06

Nested routes & Outlet

Wrap your pages in a parent route to share a layout — a navbar that stays put while the page beneath it swaps. The Outlet is where the swap happens.

Remember copying the same navbar into every blog page in Foundations, and having to update all of them whenever it changed? Nested routes fix that. You make one parent route holding shared UI (the navbar), and nest your pages inside it. The shared part stays; only the inner page swaps.

The magic word is <Outlet /> — a slot in the parent that says "put the current page here". Anything outside the Outlet (navbar, footer, sidebar) shows on every page; the Outlet itself fills with whatever the URL matches:

Code anatomy — a layout with Outlet
function Layout() { return ( <div> <Nav /> <Outlet /> </div> ) }
Hover or tap a highlighted token above · outside Outlet = every page · inside = the swapping page
—
Every part explains its own job.

In the routes file, you nest the pages inside the parent, and mark the homepage with index (meaning "the default child, shown at the parent's own path"):

routes.tsx
<Route path='/' element={<Layout />}>       // parent: navbar + outlet
  <Route index element={<Home />} />       // shows at '/'
  <Route path='about' element={<About />} />  // shows at '/about'
</Route>
// visiting /about → Layout (navbar) + About, together in the outlet
◆ Insight — you already watched this happen

Scroll back to the fake browser in section 2. The dark navbar that never moved? That's the stuff outside the Outlet — living in the parent Layout. The purple area that swapped with every click? That's the Outlet filling with the matched child page. Nesting is just how you tell React Router "keep this frame, change the picture inside it." Change the navbar once, and it updates on every page automatically.

★

Recap

Client-side routing

  • Your app stays one page; routing shows/hides components based on the URL — no reload.
  • Gives real, shareable, bookmarkable addresses like /pumpkins.
  • We use the react-router-dom package (also unlocks the browser back/forward buttons).

Setup

  • routes.tsx: a list of <Route path element /> — each pairs a URL with a component.
  • index.tsx: render <RouterProvider router={router} /> instead of <App />.
  • You set this up once per project; most challenges give it to you. Don't memorise the imports.

The moving parts

  • Link (to='/x'), never <a href> — anchors reload and wipe state; Link doesn't.
  • :param in a path = a dynamic slot. Read it with useParams(). Name must match.
  • Params arrive as strings — convert with Number() for maths. Guard with if (!id).
  • Nested routes: a parent Layout wraps child pages to share a navbar/footer.
  • <Outlet /> = the slot where the matched child page appears. Outside it = every page.
  • index route = the default child shown at the parent's own path (the homepage).
