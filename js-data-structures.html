Digging into data inside data

Real data is rarely flat. It's objects holding arrays holding objects — and the skill is calmly walking down through the layers to grab the one value you want.

Using the lecture's Star Wars dataset (Luke, his vehicles, and a Dejarik board), this guide lets you build a path and watch it resolve step by step, then run every query live.

luke.vehicles[0].model one path, four layers deep — let's take it apart.
01

What nesting is

Objects and arrays can hold each other, in any combination. Four shapes cover everything.

You already know objects ({ }, keyed values) and arrays ([ ], ordered lists). Nesting is just putting one inside the other. There are four combinations, and once you can spot which one you're looking at, navigating it becomes mechanical:

object in object
{ a: { b: 1 } }
A key whose value is another object. Reach in with .a.b.
object in array
[ {id:1}, {id:2} ]
A list of objects. Reach in with [0].id.
array in object
{ a: [1, 2] }
A key whose value is a list. Reach in with .a[0].
array in array
[ [1,2], [3,4] ]
A grid / matrix. Reach in with [row][col].
◆ Insight — read the brackets to know the shape

The outermost symbol tells you what you're holding. Starts with { → it's an object, reach in by key name. Starts with [ → it's an array, reach in by index number. The Star Wars data below starts with { (Luke is an object); the Dejarik board starts with [ (it's an array of arrays). That first character decides your first move.

02

Dot vs bracket

Two ways to reach one level in. Dot for named keys, brackets for indexes — and each layer just chains onto the last.

Every step deeper is either a .key (into an object) or a [index] (into an array). You chain them left to right, and after each one you're "standing on" whatever that step returned. Hover the four-layer path the whole guide is built around:

▲ When must you use brackets?

Dot notation only works with a key name you can type literally: obj.climate. Brackets are required for two cases: array indexes (arr[0] — you can't write arr.0), and dynamic keys held in a variable (obj[myKey]). So when the "key" is a number or lives in a variable, reach for [ ]. When it's a fixed name you know, . reads cleaner.

✖ The undefined cliff — the #1 nested-data bug

Try luke.vehicles[9].model in the explorer. There's no vehicle at index 9, so luke.vehicles[9] is undefined — and the moment you try .model on undefined, JavaScript throws "Cannot read properties of undefined (reading 'model')." This is the error you'll hit most with nested data. It always means: a step further left than you think came back empty. Read the path right-to-left from the failing key to find where it actually broke.

◆ Insight — the question to ask after every step

"What am I standing on now — an object or an array?" That single question tells you your next move: object → .key, array → [index]. The explorer's type badges (object / array / value) are training that instinct. Once it's automatic, arbitrarily deep data stops being intimidating — it's just the same two-step decision, repeated.

04

Querying with array methods

Most real queries are: navigate to an array, then apply an array method. This is where the arrays guide pays off.

Once a path lands you on an array of objects, the tools from the arrays guide take over — map, filter, find, reduce. The twist with nested data: inside the callback, you're navigating a single object again (v.name, v.specs.crew). Run all the lecture's queries here — they execute against the real data:

queries.js
// simple navigation
console.log(luke.height)                       // 172
console.log(luke.homeworld.climate)            // 'arid'
console.log(luke.vehicles[0].model)            // 'T-65 X-wing'
console.log(luke.vehicles[1].specs.passengers) // 20

// map — pull one field from every object
console.log(luke.vehicles.map(v => v.name))

// filter — keep only some objects
console.log(luke.vehicles.filter(v => v.vehicleClass === 'speeder').length, 'speeders')

// find — the first object that matches
console.log(luke.vehicles.find(v => v.vehicleClass === 'speeder').name)

// reduce — boil the whole array down to one number
console.log(luke.vehicles.reduce((total, v) => total + v.specs.crew, 0), 'total crew')

// Object.keys — what properties does this object have?
console.log(Object.keys(luke.homeworld))

?Predict the output — deprecated values
// return name + value at 90% of original, for every vehicle
luke.vehicles.map(v => ({
  name: v.name,
  deprecatedValue: v.costInCredits * 0.9
}))[0]
{ name: 'X-wing', deprecatedValue: 135000 }
X-wing costs 150000; 150000 × 0.9 = 135000. map builds a NEW object for each vehicle. Note the parentheses around ({ … }) — without them, an arrow function reads { as the start of a code block, not an object. Wrapping in () forces it to mean "return this object." That's the one syntax trap in this query.
◆ Insight — returning an object from an arrow needs ({ })

This catches everyone once. v => { name: v.name } does not return an object — the { } is read as a function body, so it returns undefined. Wrap the object in parentheses: v => ({ name: v.name }). The () tells JavaScript "this brace starts an object, not a block." Any time a map should produce objects, reach for ({ }).

?Predict the output — total crew
luke.vehicles.reduce((total, v) => total + v.specs.crew, 0)
// crews are: 1, 6, 1, 2, 1
11
reduce starts the accumulator at 0, then adds each vehicle's specs.crew as it walks the array: 0+1+6+1+2+1 = 11. The nested v.specs.crew is navigation happening inside the reduce callback — array method on the outside, path-walking on the inside.
▲ Two ways to get the first speeder

The lecture shows both, and it's a nice lesson: vehicles.find(v => v.vehicleClass === 'speeder') gets it directly, while getSpeeders(luke)[0] reuses your filter then takes index 0. Both are correct. find is marginally faster because it stops at the first match instead of scanning the whole array — but reusing existing code is also a real virtue. Neither is "the" answer.

05

Arrays in arrays: the grid

A Dejarik board is an array of arrays — a grid. Two indexes get you any square: board[row][col].

When arrays nest inside arrays, you've got a grid. The outer index picks a row (which inner array); the inner index picks a column (which item in that row). Click any square to see the exact access that reaches it:

grid.js
function getJarValue(row, col) {
  return dejarik[row][col]
}

console.log(getJarValue(0, 2))   // 'MS' — row 0, column 2
console.log(getJarValue(0, 4))   // 'GT' — row 0, column 4
console.log(dejarik[0])          // the whole first row (an array)
◆ Insight — rows can be different lengths

Nothing forces the inner arrays to match. In this board the third row (dejarik[2]) holds just one square, while the others hold six. That's fine — each row is an independent array. It also means dejarik[2][3] would be undefined (that row has no column 3), the same cliff from section 3. Grids in the wild are often ragged like this.

Recap

Navigating nested data

  • Nesting = objects & arrays inside each other. Four shapes: obj-in-obj, obj-in-arr, arr-in-obj, arr-in-arr.
  • The first character tells you the shape: { = object (use .key), [ = array (use [index]).
  • Dot .key for named object keys · brackets [i] for array indexes and dynamic keys.
  • Chain left to right; after each step ask "object or array now?" to pick the next move.
  • The undefined cliff: x.y when x is undefined throws. A step left of the error came back empty.
  • Real queries = navigate to an array, then apply map / filter / find / reduce.
  • Inside a callback you navigate a single object again: v.specs.crew.
  • Returning an object from an arrow needs ({ }) — bare { } is read as a code block.
  • Grid = array of arrays: board[row][col] — outer picks the row, inner picks the column.
  • Object.keys(obj) lists an object's property names as an array.
