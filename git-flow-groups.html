Unit 2 — Git Flow for Group Projects

Four people, one codebase, no chaos

Your first group project means several people writing code on the same repo at once. Git keeps that from turning into a mess — if you follow a shared flow. This guide walks the exact branch-per-feature loop Dev Academy recommends, and lets you resolve a real merge conflict by hand.

The scary bit is merge conflicts. They're far less scary once you've done one — so you'll do one here, safely.

branch → code → pull main → merge → push the loop you'll repeat for every feature.

When something seems wrong ("where's Sarah's navbar?"), the first question is always: is this my local main, or GitHub's main, and are they in sync? The map above is worth keeping in your head.

02

The whole loop

Every feature you build follows the same nine steps. Learn the shape once and repeat it.

Here's the entire recommended flow at a glance. It looks like a lot, but it's really just: get the latest, branch off, work, catch up with main, then merge up.

The branch-per-feature loop
Pull main — git checkout main then git pull. Start from the newest code.
Branch off — git checkout -b navbar. Name it for the feature, not yourself.
Write your code on that branch. Never on main.
Stage & commit — git add . then git commit -m "...".
Push your branch — git push (first time sets upstream). Now it's on GitHub too.
Catch up — git checkout main, git pull to grab teammates' merged work.
Merge main into your branch — back on your branch, git merge main. Resolve conflicts here, on your branch.
Push again — git push your now-updated branch.
Merge up to main — git checkout main, git merge navbar, git push. Tell the team main moved.
▲ The order that saves you: merge main into your branch FIRST

The single most important habit here: before you merge your work up into main, first pull main and merge it down into your branch. That way any conflicts get sorted out safely on your branch — where breaking things doesn't hurt anyone — instead of on the shared main that the whole team depends on. Keep main clean and always-working; do the messy resolving on your own branch.

Walkthrough, step by step

The same loop, now with the real commands and what each one does. Scroll the repo map back up as you read — every command moves code between those four boxes.

Start clean, then branch

Naming matters in a team. A branch called john tells your teammates nothing; a branch called navbar tells them exactly what you're building:

git checkout main git pull git checkout -b navbar ↑ name = the feature

Every part explains its own job.

Work, then save it up to GitHub

Write your code, then the add → commit → push chain moves it from your files, to a saved snapshot, to GitHub:

terminal — on branch: navbar
$ git add .              # stage all your changes
$ git commit -m "add navbar"   # save a snapshot on this branch
$ git push               # first push? it prints a --set-upstream line — copy & run it
branch 'navbar' set up to track 'origin/navbar'
◆ Insight — add, commit, push are three different moves

They're easy to blur together, but each hands your code to a different place. add stages which changes to include; commit saves them as a snapshot on your local branch; push sends that branch up to GitHub. Until you push, your work exists only on your computer — a teammate can't see it, and a dead laptop loses it. Push regularly, not just at the end.

Catch up with main, then merge it into your branch

While you worked, a teammate merged their feature into main. Grab it, then bring it into your branch:

terminal
$ git checkout main      # hop to local main
$ git pull               # grab the teammate's merged work from GitHub
$ git checkout navbar    # back to your branch
$ git merge main         # pull main's new code INTO your branch

If you and the teammate touched different files, this merge just works. If you touched the same lines of the same file — that's a merge conflict, and it's the next section.

Finish: merge up to main and push

Once your branch is clean and working, send it up so the team gets it:

terminal
$ git push               # push your updated branch first
$ git checkout main      # hop to main
$ git merge navbar       # bring your feature into main
$ git push               # push main up — then tell the team it moved
04

What a merge conflict is

Two people changed the same line. Git won't guess which to keep — it hands the decision to a human. That's you.

A conflict happens when two branches changed the same line of the same file in different ways. Git merges everything it safely can, but when it hits that clash, it stops and says: you both changed this — I'm not going to pick for you. It marks the spot and waits for a human.

The markers look alarming the first time. They're just three lines wrapping the two versions:

Code anatomy — the conflict markers
<<<<<<< HEAD <h1>Hello, I hope you have a good day</h1> ======= <h1>Hello {name}</h1> >>>>>>> main
Hover or tap a highlighted token above · yours on top, theirs below, markers to delete
—
Every part explains its own job.
◆ Insight — the two words VS Code uses

VS Code shows clickable options above the conflict: Accept Current Change (keep yours), Accept Incoming Change (take theirs), Accept Both, or Compare. "Current" = the branch you're on; "Incoming" = the branch flowing in. Whichever you pick, VS Code deletes the markers and leaves clean code. You can also just edit by hand — delete the markers and the versions you don't want, keep what you do. There's no wrong tool; the decision is the human part.

▲ Resolving is a team conversation, not a solo guess

When both versions matter, don't just silently pick yours. This is exactly the moment to message the teammate whose code you're merging: "we both changed the greeting heading — want to hop on a call?" Often the answer is "keep both" or a blend. Conflicts aren't a git problem to hide; they're a signal that two people's work met, and a two-minute chat resolves them better than a guess.

Resolve one yourself

Here's a real conflict, exactly as it'd appear in VS Code. Pick an option and watch the markers disappear into clean code — then finish the merge.

You merged main into your greetings branch and hit a conflict: you both edited the heading. Click one of the resolution options — just like the buttons VS Code floats above the conflict:

merge conflict Greetings.tsx
resolve the conflict
☐ 1 · Resolve the conflict (pick an option above)
☐ 2 · git add .
☐ 3 · git commit -m "resolve merge conflict"
☐ 4 · git push
✖ After resolving, it's still a normal commit

People forget the conflict isn't "done" the moment the markers vanish. Resolving edits the file — you still have to git add, git commit, and git push like any change, or the merge stays half-finished. And always double-check no markers are left behind: a stray <<<<<<< or ======= in your code will break the app. Search the file for them before you commit.

★

Recap & cheat sheet

The mental model

  • Code lives in up to 4 places: GitHub main, GitHub your-branch, local main, local your-branch.
  • They drift apart as the team works. Always ask "which one am I looking at?"
  • Never work on main. Branch per feature; keep main clean and always-working.
  • Name branches for the feature (navbar, about-page), not yourself.

The loop (copy this)

  • git checkout main · git pull — start fresh
  • git checkout -b feature — branch off (-b = create + switch)
  • write code · git add . · git commit -m "..." · git push
  • git checkout main · git pull — catch up with teammates
  • git checkout feature · git merge main — resolve conflicts HERE
  • git push · git checkout main · git merge feature · git push

Conflicts

  • Happen when two branches change the same line of the same file.
  • Markers: <<<<<<< HEAD (yours) · ======= (divider) · >>>>>>> main (theirs).
  • VS Code: Accept Current (yours) / Incoming (theirs) / Both — or edit by hand.
  • Resolve on your branch, talk to the teammate, then add · commit · push.
  • Check no markers left behind before committing — they break the code.
  • Merge main into your branch often → smaller, rarer conflicts.
