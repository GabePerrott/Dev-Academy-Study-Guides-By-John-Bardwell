Unit 1 · T12 — Vite & Data Models

The tool that serves your site, and the shapes your data keeps

Two lighter, mostly-conceptual topics. Vite is the build tool that's been quietly running your websites since Foundations — here's what it actually does. Data models are how you keep your data's shape consistent across a whole app.

Less code to grind through than usual — but you'll use both in nearly every challenge from here, so they're worth the half hour.

$ npm run dev the command that starts Vite — you've typed it before without knowing what it did.
01

What Vite is

A web development build tool. Its job: take your HTML/CSS/JS and serve it to a browser, fast.

You've already been using Vite — every time you ran your Foundations blog and saw your pages in the browser, that was Vite. You just didn't have a name for it. It's a build tool (site vitejs.dev), and from now on it runs behind basically every challenge you'll do.

Two things make it worth understanding rather than treating as magic: how it serves your code (fast, via on-demand loading) and the dev server it gives you (with instant live updates). Those are the next two sections.

◆ Insight — the name is the whole pitch

"Vite" is French for quick. Speed is the entire selling point — both how fast your site loads and how fast you see your edits while building. Everything about how it works, below, is in service of not making you wait.

02

Bundling vs on-demand

The old way shipped your whole app at once. Vite ships only the piece the browser is asking for.

Bundling was the old approach: your entry file loads modules, which load more modules, and the whole web of code gets wrapped into one big file that's sent to the browser. It works, but it's slow to assemble and wasteful — the entire bundle ships no matter which page you actually want.

On-demand compilation is Vite's trick. Using ES modules (the import/export you know), it sends only the code needed for what you're doing, when you ask for it. Try both modes — open a page and watch what ships:

◆ Insight — why on-demand is faster

In bundling, visiting the Home page still ships the Dashboard's chart code, the admin panel, everything — because it's all one file. Vite sends just Home's code, so there's less to build and less to download. The bigger your app grows, the more that difference compounds. That's the practical reason Vite feels snappy where old tools dragged.

▲ Nuance — bundling isn't dead

On-demand is how Vite behaves in development (while you're building). For the final production version that real users load, Vite still bundles — a polished single package is actually better once the code's finished. So it's not "bundling bad, on-demand good"; it's the right tool at each stage. You don't need to configure any of this yet — just know both exist.

03

Dev server, HMR & ports

Vite runs a local server for you, updates the page the instant you save, and lives on predictable ports.

Run npm run dev (sometimes npm start — the README tells you which) and Vite starts a development server, printing a localhost address you open in the browser. It's the thing that makes your site actually appear.

Hot Module Replacement (HMR)

The best part: change a value in VS Code, hit save, and the page updates immediately — no manual refresh. That instant feedback loop is called Hot Module Replacement, and once you're used to it you'll never want to go back.

◆ Insight — HMR often keeps your place

HMR doesn't just reload — where it can, it swaps only the changed module and preserves the page's state. Tweaking a button halfway down a long form? The page updates without scrolling you back to the top or wiping what you'd typed. Small thing, but it saves a surprising amount of friction over a day.

The two ports

During bootcamp you'll see two localhost ports, and they're not interchangeable:

Port 5173

The front end — the web page the user sees in the browser. Vite's default. This is the one you'll open most.

Port 3000

The back end — a server doing the heavier work with databases. Comes in from the next unit onward.

▲ "Port already in use" is not an error

If you've already got a server running in another terminal, Vite won't fight it — it just bumps to the next free port: 5174, then 5175, and so on. So if your site shows up on 5174 instead of 5173, nothing's broken; you probably left an old server running. Check the address Vite actually prints rather than assuming 5173.

04

vite.config.js

One config file where Vite's settings and plugins live. You'll mostly read it, not write it — for now.

Vite reads its settings from a vite.config.js file, much like TypeScript has its own config. It's where you change how things behave and add extra tools (called plugins) by importing and registering them. Here's a typical one — the kind you'll meet from the next unit, with the React plugin set up. Hover the parts:

Code anatomy — a vite.config.js
import { defineConfig } from 'vite' import react from '@vitejs/plugin-react' export default defineConfig({ plugins: [react()] })

Its value right now is diagnostic: if you're ever curious how a project is wired, or a README mentions a plugin, vite.config.js is where the answer lives. Reading it is a skill; writing it comes much later.

05

Data models: the three concepts

A data model is a deliberate, consistent shape for the data your app cares about. It rests on three ideas.

Say your app has users. A data model decides exactly what a "user" looks like in your code — which properties, of which types:

user.js
// a user, modelled: only the fields the app actually uses
const user = {
  id: 1,
  username: "rey",
  email: "rey@example.dev",
  age: 28
}

console.log(user.username)      // 'rey'
console.log(typeof user.age)    // 'number'
// note: no cat's name, no grandmother's phone — we don't model what we won't use
Structure

Defines the types of each piece (string, number) and how data relates. Simple here — all top-level. Later a user might hold a nested pet object.

Abstraction

Include only what you'll use. Real users have endless details; your model keeps the handful the app needs. A simplified, workable view.

Consistency

Use the same model everywhere, so a user looks identical in every corner of the app. No surprises about what fields exist.

◆ Insight — abstraction is the same instinct as the bowling model

Deciding to model id, username, email, age and ignore the rest is exactly the move from the bowling challenge — capturing only the relevant parts of a real thing. "What does the app actually need to know?" is the whole question. Modelling too much is as much a mistake as modelling too little; extra fields are clutter you have to keep consistent for no benefit.

06

Interfaces as contracts

A TypeScript interface writes your data model down as an enforceable shape — a promise every object of that type must keep.

An interface defines the shape of an object: which keys it has and the type of each value. Think of it as a contract — declare an object to be a User, and it must have exactly this shape, or the tooling complains before you ever run the code. Hover the parts:

Code anatomy — a TypeScript interface
interface User { id: number username: string email: string age: number }

▲ Insight — interfaces vanish when the code runs

Here's the surprising part: interfaces exist only while you're writing code. TypeScript uses them to catch mistakes and power VS Code's autocomplete, then erases them when compiling to the JavaScript that actually runs. So an interface never slows your app down or exists at runtime — it's a dev-time safety net and a piece of documentation, nothing more. That's why the checker above validated a plain JS object: the interface is a description laid over ordinary data.

◆ Insight — documentation that can't lie

A comment saying "user has an id, name, email" can drift out of date the moment someone changes the code. An interface can't — if the object stops matching, the compiler complains. So interfaces double as documentation the tooling keeps honest. Someone new can read your models/ folder and understand your whole data shape in a minute, and trust that it's current.

07

Shared models

Define each model once, import it everywhere — front end and back end alike. One source of truth.

Unified (or shared) data modeling means using a single set of models across your whole full-stack app — the front end the user sees and the back end talking to the database. Define the User interface once in its own file, then import it wherever you need it. Both sides agree on what a user is because they're literally reading the same definition.

At Dev Academy the convention is a models/ directory at the project root:

my-project/ ├── models/ # shared data models live here │ └── user.ts # exports the User interface ├── client/ # front end — imports User from ../models/user ├── server/ # back end — imports the SAME User └── package.json
◆ Insight — one definition, zero drift

The payoff is a single source of truth. Add a phone field to the User in models/user.ts, and both the front end and back end instantly know about it — the type flows everywhere it's imported. Without shared models you'd define "user" twice and they'd quietly disagree the first time someone updated one and forgot the other. This is the DRY principle (don't repeat yourself) applied to the shape of your data.

★

Recap

Vite

  • Vite = a fast web build tool + dev server. You've used it since Foundations.
  • Bundling = ship all code as one file. On-demand = ship only what's needed, when needed.
  • Vite uses on-demand in dev, still bundles for production.
  • HMR (Hot Module Replacement) = edits show in the browser instantly, no refresh.
  • Run it with npm run dev (sometimes npm start). Front end 5173, back end 3000.
  • "Port in use" just bumps to 5174/5175 — not an error. Read the address Vite prints.
  • vite.config.js holds settings & plugins (defineConfig + a plugins array). Mostly read, not written.

Data models

  • A data model = a consistent shape for the data your app cares about.
  • Three ideas: structure (types & relationships), abstraction (only what you use), consistency (same shape everywhere).
  • A TypeScript interface writes the model down: keys + their types.
  • An interface is a contract — objects typed as it must match, or the tooling complains.
  • Interfaces are erased at runtime — a dev-time safety net + honest documentation.
  • Shared models: define once, import in front and back end. One source of truth (DRY).
  • Convention: keep them in a models/ folder at the project root.
