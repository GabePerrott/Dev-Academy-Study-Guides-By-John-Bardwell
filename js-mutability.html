Mutability, and the case of the object that changed itself

A deeper look at the trickiest idea from T3: why editing one variable can silently change another. It's the source of a whole category of "wait, why did that happen?" bugs — and once you can picture what's in memory, it stops being spooky.

01

Mutable vs immutable

"Mutable" just means changeable after it's created. The whole lesson hinges on which values are which.

Two buckets, same as before — primitives and reference types. The bucket a value lands in decides whether you can change it in place:

Immutable

Primitives

string · number · boolean · undefined · null · symbol · bigint

Can't be changed once created. There's no way to turn the value 5 into something else — five is five forever. You can only point a variable at a different value.

Mutable

Reference types

object · array · function

Can be changed in place. You can edit an object's contents — swap the water bottle's water for coffee — and it's still the same object, just mutated.

✖ The distinction people trip on — mutate vs reassign

"You can't change a primitive" and "you can change a number variable" both sound true, and they are — because they're different actions. Reassigning means pointing a variable at a brand-new value (number = 500). Mutating means editing the contents of the thing a variable already points to (bottle.contents = "coffee"). Primitives only allow reassignment. Objects allow both. Keep these two verbs separate and the rest of this page is easy.

Code anatomy — spot the two different "="
const bottle = { contents: "water" } bottle.contents = "coffee"

mutate-vs-reassign.js
// primitive: can only REASSIGN (point at a new value)
let n = 5
n = 500
console.log("reassigned:", n)

// object: can MUTATE in place, even as a const
const bottle = { contents: "water" }
bottle.contents = "coffee"     // editing the box, not reassigning it
console.log("mutated:", bottle)
▲ Reminder — const is not "immutable"

A const object can still be mutated, which surprises everyone at first. const locks the variable (you can't reassign bottle to a new object), but it doesn't lock the contents. If you truly want a frozen object, that's a separate tool — Object.freeze() — not const.

02

Pass by value

Primitives travel as copies. Hand one to a function and the original is untouchable.

When you pass a primitive into a function, you don't pass the variable — you pass a copy of its value. The lecture's metaphor: giving someone your phone number. They can save it, change how it's labelled in their contacts, scribble on it — your actual number never changes. It was only ever a copy.

pass-by-value.js
let number = 7

function changeNumber(n) {
  n = 123              // only changes the local copy
  return n
}

const newNumber = changeNumber(number)

console.log("returned:", newNumber)   // 123
console.log("original:", number)      // still 7 — untouched

◆ Insight — why this is the "safe" one

Because primitives copy, you never have to worry about a function secretly altering a number or string you passed in. There's no action-at-a-distance. This is exactly why the lecture says: with primitives, "there's nothing to worry about." Save your caution for the next section.

03

Pass by reference

Objects travel as shared addresses. Hand one to a function and it can reach back and change your original.

Objects and arrays don't get copied when you pass them. What travels is a reference — the memory address where that object lives. The function walks to that address and edits the real thing. Now the metaphor flips: you're not handing over your phone number, you're handing over your actual phone. If they smash it, it's genuinely smashed — there's only one, and you both hold its address.

▲ What "in memory" actually means

Every object your program creates is stored at some location in the computer's memory. A variable holding an object doesn't contain the object itself — it contains a pointer to that location. Do const b = a with an object and you copy the pointer, not the object. Two variables, one underlying box. Edit through either name and the single shared box changes.

pass-by-reference.js
const myPhone = { model: "Pixel", condition: "pristine" }

function destroyPhone(phone) {
  phone.condition = "smashed"    // edits the shared object directly
  return phone
}

const destroyed = destroyPhone(myPhone)

console.log("returned:", destroyed.condition)   // "smashed"
console.log("original:", myPhone.condition)     // also "smashed"  ← side effect!

Flip the memory lab above to its second tab — Pass by reference — and step through. This time both variables point at one box, and the mutation flashes through to both.

✖ The bug this causes — "side effects"

A function that changes an object you passed in has a side effect: it reached outside itself and altered your data. Sometimes that's intended; often it's a nasty surprise, because the function's name gave no hint it would touch your original. Whole afternoons get lost to "but I never changed that array!" — when a function you called quietly did.

?Predict the output
const list = [1, 2, 3]

function addFour(arr) {
  arr.push(4)

const result = addFour(list)
console.log(result)
console.log(list)         // did the original change?
[ 1, 2, 3, 4 ]
[ 1, 2, 3, 4 ]
Both. list and arr are two names for the same array in memory, and push mutates it in place. The original changed even though you only "meant" to change the copy inside the function — because there was no copy.
04

Copying safely

The fix the lecture points at: when in doubt, work on a copy — not the original.

If passing an object around risks mutating the original, the safe move is to make a fresh copy first and edit that. The everyday tool is the spread operator: {...obj} for objects, [...arr] for arrays. It builds a new box with the same contents, at a new address.

copy-safely.js
const myPhone = { model: "Pixel", condition: "pristine" }

function safeDestroy(phone) {
  const copy = { ...phone }       // new object, new address
  copy.condition = "smashed"
  return copy
}

const destroyed = safeDestroy(myPhone)

console.log("returned:", destroyed.condition)   // "smashed"
console.log("original:", myPhone.condition)     // "pristine" — safe!

▲ The catch — spread is a shallow copy

{...obj} copies the top level only. If a property is itself an object or array, the copy still shares that inner box with the original. For a fully independent deep copy, reach for structuredClone(obj). You won't need deep copies often yet, but remember the word "shallow" exists so a future bug makes sense.

◆ Insight — this connects straight to the array methods

This is the quiet reason map and filter feel so safe: they return new arrays and leave the original alone. Compare that to push, sort, and splice, which mutate the array in place. When you want to avoid side effects, prefer the methods that hand you a new array over the ones that edit the one you've got.

★

Recap

The whole deep dive in eight lines.

  • Primitives are immutable and pass by value (a copy) — originals are always safe.
  • Objects & arrays are mutable and pass by reference (a shared address).
  • Reassign = point a variable at a new value. Mutate = edit the contents of the existing box.
  • const blocks reassignment, not mutation. Use Object.freeze() for real immutability.
  • Passing an object to a function can change your original — that's a side effect.
  • Work on a copy to stay safe: {...obj} / [...arr] (shallow), structuredClone() (deep).
  • map / filter return new arrays (safe); push / sort / splice mutate in place.
  • Metaphor: sharing a phone number (by value) vs handing over the phone itself (by reference).
