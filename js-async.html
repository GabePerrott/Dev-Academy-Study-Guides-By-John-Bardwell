Code that waits without freezing

Every time you fetch from an API, your code has to wait for a reply that might take a second to arrive. Async JavaScript is how it waits politely — starting the request, letting the rest of the page keep working, and picking up the result the moment it lands.

You've already used async and await in the API guides. This one explains what they actually do underneath, so they stop feeling like magic words.

start it → keep going → come back for the result
01

Why async exists

JavaScript does one thing at a time. Slow things would freeze the page — unless it can set them aside.

JavaScript runs on a single thread — one line at a time, in order. That's usually fine, because most lines finish instantly. But some things are slow: fetching from a server, reading a file, a timer. If JS just stopped and waited for a network reply, the whole page would lock up — no clicking, no scrolling — until it came back.

◆ Analogy — ordering a book

Think of a slow task like ordering a book that isn't in stock. You don't stand frozen at the counter until it arrives. The shop takes your order, hands you a receipt, and you go do other things. When the book arrives, you come back and collect it. Async code works the same way: the slow task hands back a receipt now, and you collect the real result later. That receipt is called a Promise.

02

Promises

A Promise is a placeholder for a value that isn't here yet. It's in one of three states.

A Promise is an object representing a value you'll have eventually. When you call fetch(), you don't get the data — you get a Promise for the data. It lives in one of three states:

Code anatomy — the three states of a promise
pending → fulfilled (got the value) → rejected (got an error)
Hover or tap a state · a promise starts pending, then settles once — either fulfilled or rejected
—
Each state explains itself.

The old way to read a settled promise is .then() for success and .catch() for failure:

promise-then.js
fetch('/api/sharks')
  .then(res => res.json())   // when it arrives, turn it into data
  .then(data => console.log(data))
  .catch(err => console.log('failed:', err))

It works, but the chain gets awkward fast. That's why async/await exists — same promises, nicer to read.

03

async / await

Syntactic sugar over promises. It lets asynchronous code read top-to-bottom, like the sync code you're used to.

Code anatomy — an async function
async function getSharks() { try { await fetch('/api/sharks') } catch (err) { handleError(err) } }
Hover or tap a token · async unlocks await · await unwraps the value · try/catch handles rejection
—
Each keyword explains its job.

Here's the same shark fetch from section 2, rewritten. Notice it reads like a straight list of steps:

get-sharks.js
async function getSharks() {
  const res  = await fetch('/api/sharks')   // wait for the reply
  const data = await res.json()             // wait for the body to parse
  return data
}
▲ Two awaits, not one — the classic trap

A fetch usually needs two awaits: one for the response to arrive, and a second for .json() — because reading the body is also async. Forget the second one and data is a Promise, not your object. This is the same trap flagged in the Consuming APIs guide.

04

What runs when

The part that trips everyone up: awaited code doesn't run in the order it's written. Trace it and see.

When JS hits an await, it pauses that function and lets the rest of the program run. The awaited work finishes later. So synchronous lines after an async call often log first. Press run and watch the real order:

◆ The rule in one line

Everything up to the first await runs immediately, in order. Everything after an await is set aside to run once the promise settles — which is almost always after the synchronous code that follows the function call. Async doesn't mean "later" for the whole function; it means "later" for the part after the await.

05

Common gotchas

Four mistakes that produce confusing bugs — and the tell for each.

Forgetting await

Without it you hold the Promise, not the value. The tell: your variable logs as Promise { <pending> } instead of the data. Add the missing await.

await outside an async function

It's a syntax error. await is only legal inside a function marked async. If you need it at the top level, wrap it in an async function and call that.

Forgetting the error path

Networks fail. An awaited fetch that rejects with no try/catch around it becomes an unhandled rejection. Wrap awaited calls that can fail in try/catch.

✖ In React, you rarely write this by hand

Once you're in components, React Query runs your async function for you and hands back isPending, error, and data — no manual try/catch in the component. But it's calling an async function underneath. Understanding this is what makes that one make sense.

★

Recap

The mental model

  • JS runs one thing at a time; async lets slow tasks run without freezing the page.
  • A Promise is a placeholder for a future value: pending → fulfilled or rejected.
  • async unlocks await and makes a function return a Promise.
  • await pauses the function and unwraps the value — you get data, not a Promise.
  • try/catch handles a rejected promise inside async functions.

Watch out for

  • A fetch needs two awaits — one for the response, one for .json().
  • Code after an await runs later than the sync code after the call — trace the order.
  • Missing await → you're holding a Promise, not the value.
