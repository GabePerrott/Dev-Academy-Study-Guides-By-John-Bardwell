Unit 2 — Consuming APIs

Fetching data from somewhere else

Until now your data has been hardcoded in your app. APIs let you fetch live data from a server — weather, pokémon, movies, anything. This guide covers what an API is, how you ask it for things, and the React pattern for loading that data into your components without freezing the page.

It pulls together threads from across the course: async/await, JSON, state, and the effects that run when a component loads.

request → wait → JSON → state → render the shape of every data fetch you'll write.
01

What an API is

A doorway to someone else's data. You send a request to a URL; it sends back data — usually JSON.

API stands for Application Programming Interface, but the words don't help much. The useful picture: an API is a waiter at a restaurant. You don't walk into the kitchen and cook — you tell the waiter what you want, they go fetch it, and bring back a plate. You never see the kitchen (the server and database); you just make polite, specific requests and get data back.

Concretely: you send an HTTP request to a URL called an endpoint — like api.weather.com/today?city=wellington — and the server sends back data, almost always as JSON (the same key-value shape you know from objects). Your app then displays it.

◆ Insight — you've been consuming APIs already, sort of

Every website you use is quietly making API requests — scrolling a feed, checking a price, loading a map. The difference now is you're the one writing the request. And because the data lives on someone else's server, two new realities appear: it takes time to arrive (the network isn't instant), and it can fail (servers go down, URLs change). Most of this guide is really about handling those two facts gracefully.

02

Methods & status codes

The HTTP method says what you want to do; the status code says how it went.

Every request carries a method — a verb saying what you intend. Four cover almost everything:

MethodMeansRestaurant analogy
GETRead data. Fetch and display something."Bring me the menu."
POSTCreate new data. Send something to be added."I'd like to place an order."
PUTUpdate existing data."Change my order to no onions."
DELETERemove data."Cancel my order."

When you're just displaying data — which is most of what you'll do first — you use GET. The server replies with a status code, a three-digit number telling you how it went. You don't need all of them, just the families:

2xx
Success

It worked. 200 OK is the one you want — data's on its way.

4xx
You messed up

Bad request. 404 Not Found (wrong URL), 401 (not allowed in).

5xx
They messed up

The server broke. 500 — not your fault, their problem. Try again later.

▲ The memory hook for status codes

2xx = all good. 4xx = you did something wrong (mistyped the URL, missing permission). 5xx = the server did something wrong. That 4-vs-5 split is the useful instinct: a 404 means check your request; a 500 means it's not you, wait and retry. When a fetch misbehaves, the status code is the first clue about whose problem it is.

04
fetch & async/await

      
fetch is the built-in function that makes requests. It returns a promise — so you await it, twice.


      
The browser gives you fetch to make requests. Because a request takes time, fetch
      returns a promise — the same promises from the testing guide's findBy. So you
      await it, inside an async function:


      

        
Code anatomy — a fetch, start to finish

        
async function getStudents() {
  const response = await fetch(url)
  const data = await response.json()
  return data
}

        
Hover or tap a highlighted token above · two awaits: one for the response, one for the JSON
—
Every part explains its own job.

      


      

        
✖ The two-await trap that catches everyone

        
You await twice, and forgetting the second is the most common fetch bug. The first
        await gets the response — a wrapper with the status code and headers, but not your data. The second,
        await response.json(), unwraps the actual JSON body. Skip it and you'll be staring at a
        confusing Response object or a Promise, wondering where your data went. Response first, then
        .json().

      


      

        
?Spot the bug

        

          
const response = await fetch(url)
const data = response.json()   // ← what's wrong here?
console.log(data)

          
          

            
data is a Promise, not your JSON

            
The await is missing on response.json(). Since
            .json() returns a promise, without await you store the promise itself, not the
            resolved data. Fix: const data = await response.json(). This exact slip is behind most "why
            is my data undefined / a Promise?" moments.

          

        

      

    


    
    

      
05
Fetching in React

      
Fetch when the component loads, store the result in state, and the component re-renders with the data. useEffect handles the "when it loads" part.


      
In React the pattern is always the same shape: fetch → store in state → render. Two questions: where
      do you put the data (state), and when do you fetch it (when the component first appears). That "when it loads"
      timing is what useEffect is for:


      

        
Code anatomy — the data-fetching component

        
const [students, setStudents] = useState([])

  useEffect(() => {
    getStudents().then(setStudents)
  }, [])

  return students.map(s => ...)

        
Hover or tap a highlighted token above · fetch in useEffect · store in state · render
—
Every part explains its own job.

      


      

        
✖ The empty [] is not optional

        
That empty dependency array [] at the end of useEffect is critical. It means
        "run this effect once, when the component first loads." Forget it, and the effect runs on every
        render — but fetching sets state, and setting state causes a render, which runs the effect, which fetches
        again... an infinite loop hammering the API. If your app is firing endless requests, a missing
        [] is almost always why.

      


      

        
◆ Insight — it all connects here

        
Look at how many earlier pieces show up: useState and .map() from the React
        guide, async/await and promises from testing, JSON from data models, even the "start with an
        empty array so nothing crashes" instinct from the undefined cliff. Consuming APIs isn't a new island — it's
        where the whole course so far clicks together into something that feels like a real app.

      

    


    
    

      
06
Loading & error states

      
Because data takes time and can fail, a good component tracks three situations — not just the happy one.


      
A real fetch has three possible states, and beginners only handle one (success). The network takes
      time, and it can break — so your component should know which situation it's in:


      

        
⏳ Loading
The request is out, data hasn't arrived. Show a spinner or "Loading…" so the user knows something's happening.

        
✓ Success
Data arrived. Render it. The state you always remember to build.

        
✖ Error
The request failed (404, 500, no internet). Show a friendly message, not a blank or broken page.

      


      
You track this with a little state — either a status string, or a loading boolean plus an error value. Then
      you render different UI for each:


      

        
StudentList.tsx

        
const [status, setStatus] = useState('loading')  // 'loading' | 'success' | 'error'

// in your fetch: setStatus('success') when it works,
// setStatus('error') inside a catch when it throws

if (status === 'loading') return <p>Loading…</p>
if (status === 'error')   return <p>Something went wrong</p>
return <ul>{students.map(...)}</ul>       // success

      


      

        
▲ try / catch is how you catch the failure

        
To handle errors you wrap the fetch in a try / catch: the try holds the happy
        path (fetch, parse, setStatus('success')), and the catch runs if anything throws —
        that's where setStatus('error') goes. Without it, a failed request throws an uncaught error and
        your app shows a blank or broken screen. Assume the network will fail sometimes, and your users get
        a graceful message instead of a mystery.

Recap

      

        
The concepts

        
    
          
  • An API is a waiter: you send a request to an endpoint (URL), it returns data as JSON.
    • 
          
  • Methods: GET (read) · POST (create) · PUT (update) · DELETE (remove). Displaying data = GET.
    • 
          
  • Status codes: 2xx good · 4xx you erred (404 wrong URL) · 5xx server erred (500).
    • 
        

      

      

        
Fetching

        
    
          
  • fetch(url) returns a promise → await it. GET is the default.
    • 
          
  • Two awaits: await fetch(url) for the response, then await response.json() for the data.
    • 
          
  • In React: fetch in useEffect(() => {...}, []), store in state, render from state.
    • 
          
  • The empty [] = run once on load. Forgetting it = infinite fetch loop.
    • 
          
  • Default state to an empty array so .map() is safe before data arrives.
    • 
        

      

      

        
Real-world robustness

        
    
          
  • Handle three states: loading, success, error — not just success.
    • 
          
  • Wrap the fetch in try / catch; set the error state in the catch.
    • 
          
  • Show a spinner while loading and a friendly message on error.
    • 
          
  • Dig into nested JSON with the dot/bracket paths from the data-structures guide.
