Data types

What kind of thing is this value? JavaScript answers with typeof — and occasionally lies to you.

Primitive types

Primitives are the simple, indivisible values. There are seven of them. A handy shortcut for strings: it's basically anything between quotes — single '…', double "…", or backticks `…` (backticks let you drop variables into the middle with ${ }).

◆ Insight — undefined vs null

They look similar but carry different intent. undefined is JavaScript saying "nobody gave this a value yet." null is you saying "this is intentionally empty." Same emptiness, opposite authors — one is an accident waiting to be filled, the other is a decision.

✖ Gotcha — the famous typeof null bug

typeof null returns "object", not "null". This is a genuine 20-year-old bug in the language: in the very first JavaScript, values were tagged by a few bits, and null happened to share the tag used for objects. Fixing it would break too much old code, so it's frozen forever. Not logic you can reason your way to — just memorise it. It will catch you when you check a value's type and forget this one exception.

Number has a few surprises

Everything numeric is just number — integers, decimals, negatives, Infinity, and even NaN ("not a number"). Yes: the value literally called "not a number" reports its type as number. JavaScript is committed to the bit.

numbers.js
console.log(typeof 42)         // integer
console.log(typeof 3.14)       // decimal, still a number
console.log(typeof -7)         // negatives too
console.log(typeof Infinity)   // yep
console.log(typeof NaN)        // "not a number" is... a number
console.log(NaN === NaN)       // and this one is wild
▲ Worth knowing — NaN never equals itself

NaN === NaN is false. It's the only value in the language that isn't equal to itself. So you can't check for it with ===; use Number.isNaN(x) instead. You'll usually meet NaN when a conversion fails — like turning the letter "A" into a number.

Casting: changing a value's type on purpose

Values in JS aren't married to their type — you can convert between them with the capital-letter "casting functions": Number(), String(), Boolean(). Whether it works depends on whether the value has a sensible equivalent.

casting.js
const strNum = "342"
const num = 342

console.log(Number(strNum))        // "342" -> 342 (amber = number)
console.log(String(num))           // 342 -> "342" (green = string)
console.log(typeof Number(strNum)) // proof it really changed
console.log(Number("A"))           // no numeric equivalent... NaN

In the lecturer's terminal the only visual clue was colour — 342 in amber meant number, 342 in green/white meant string. This guide keeps that convention, so the console above is doing the same tell.

== vs === — the equality trap

Two equals checks value only, coercing types to match first. Three equals ("strict equals") checks value and type — no coercion. This table is worth internalising:

◆ Insight — just use ===

The loose == rules are so surprising that basically every professional codebase bans it. Default to === everywhere. If you ever need a type change, do it explicitly with a casting function so the intent is visible, rather than letting == guess for you.

Non-primitive (reference) types

On top of primitives sit the "reference" types: object, array, and function. Here's the catch the lecturer flagged — typeof an array returns "object". Under the hood, arrays are a kind of object. We treat them as separate ideas when we code, but typeof can't tell them apart.

Pass by value vs pass by reference

This is the deepest idea in the chapter, and the source of a lot of "why did my object change?!" confusion later. Primitives are copied by value; references are shared by reference.

By value

primitives — the value is the thing
num342
↓ copy into b
b342 (its own copy)

Change b and num is untouched. You handed over a photocopy. And 342 itself can never change — you can only point the variable at a different number.

By reference

objects/arrays — the variable holds an address
bottle→ 📦 { color: "blue" }
↓ both point at the SAME box
copy→ 📦 { color: "blue" }

Change copy.color and bottle.color changes too — same box, two labels. You handed over the address, not a photocopy.

▲ Worth knowing — const doesn't freeze objects

You can do const bottle = { color: "blue" } and then bottle.color = "red" — and it works. const only stops you reassigning the variable (pointing it at a new box). It does nothing about editing the contents of the box it already points to. That's why the lecture could mutate a const object and array without error.

reference.js
const bottle = { color: "blue" }
const copy = bottle          // NOT a photocopy — same address
copy.color = "red"           // edits the shared box
console.log(bottle.color)    // did the "original" change?

let a = 10
let b = a                    // this IS a photocopy (primitive)
b = 99
console.log(a)               // unaffected

02

Functions

In JavaScript, functions are values you can pass around like any other. That single fact unlocks most of the "advanced" stuff.

Functions are "first-class citizens"

That intimidating phrase means exactly three things. A function can be:

  • assigned to a variable — const greeting = helloWorld
  • passed as an argument to another function — doThing(helloWorld)
  • returned from a function — return helloWorld

In other words: functions behave like numbers or strings. Anywhere you can put a value, you can put a function. Everything clever with functions is just a combination of these three moves.

◆ Insight — the parentheses are the whole ballgame

The single most useful rule of thumb: greeting is the function itself (you're referring to it). greeting() — with parentheses — calls it and gives you back its result. Passing a function to another function? Leave the parens off, or you'll pass the result instead of the function. This one distinction causes an enormous share of early bugs.

first-class.js
function helloWorld() {
  return "hello world"
}

// 1. assign to a variable
const greeting = helloWorld
console.log(greeting())            // call it via its new name

// 2. pass as an argument
function sayHello(fn) {
  const result = fn()              // call whatever function we were handed
  console.log("passed in:", result)
}
sayHello(helloWorld)               // note: no parens on helloWorld here

// 3. return from a function
function getGreeting() {
  return helloWorld                // hand the function back
}
console.log(getGreeting()())       // call getGreeting, then call its result

Three ways to write a function

Same idea, different syntax. You'll read all three constantly, so recognise them on sight.

Named function

The classic. Has a name in the declaration, uses return, callable anywhere by name.

named
function add(a, b) {
  return a + b
}
add(1, 2) // 3

Anonymous function

Identical, but with no name. On its own it's unusable — there's nothing to call it by. So you assign it to a variable, and that variable becomes its name.

anonymous
const add = function(a, b) {
  return a + b
}
add(1, 2) // 3 — same as the named one

Arrow function

The concise modern form. With curly braces you write an explicit return. Drop the braces and the return becomes implicit — the expression after the arrow is returned automatically.

arrow
// explicit return (braces + return keyword)
const add = (a, b) => {
  return a + b
}

// implicit return — no braces, no return keyword
const add = (a, b) => a + b   // same result, one line
Code anatomy — the arrow function, part by part

Higher-order functions

A "higher-order function" is just a function that takes and/or returns other functions — you already met them above under "first-class." Here's the pattern doing real work. One planEvent function produces different messages depending on which function you feed it.

higher-order.js
const birthday   = (a, b) => `${a}: it's your birthday, ${b} is invited to the pizza party!`
const graduation = (a, b) => `${a}: come celebrate ${b}'s graduation!`
const matariki   = (a, b) => `Everyone: ${a} and ${b} are organising for Matariki.`

// planEvent takes a FUNCTION and plugs the names in
function planEvent(messageFn, friend) {
  const myName = "John"
  return messageFn(myName, friend)
}

console.log(planEvent(birthday, "Yugi"))
console.log(planEvent(graduation, "Kiana"))
console.log(planEvent(matariki, "Leo"))

Functions that build functions (closures)

The trickiest example in the lecture: a function returns a customised function. Below, makeGreeter bakes in a greeting word and hands back a fresh function that remembers it. That "remembering" is called a closure — the inner function keeps hold of the variables it was created with.

closures.js
function makeGreeter(word) {
  // returns a NEW function that remembers `word`
  return (name) => `${word}, ${name}!`
}

const heya = makeGreeter("Heya")
const hi   = makeGreeter("Hi")

console.log(heya("Pri"))   // uses "Heya"
console.log(hi("Pri"))     // same input, different baked-in word
◆ Insight — you don't need to master closures today

Closures are famous for melting beginners' brains, and you'll circle back to them many times. The one-line version to hold onto: a function remembers the variables that were around when it was created, even after that outer function has finished. That's it. The mechanics will click with repetition — don't force it now.

const double = n => n * 2

console.log(apply(n => n + 1, 5))

apply just calls whatever function it's handed on x. The second call passes an inline arrow straight in as the argument — completely normal, since functions are values. And typeof a function is its own thing: "function".

Array methods

Built-in loops that take a function. They replace most manual for loops — and once they click, you won't go back.

Each of these methods walks an array for you and runs a function you supply on every item. The lecture's food metaphor is the fastest way to remember what each one gives back:

🍳
forEach
Do something with each item. Just side-effects.
returns undefined
🔍
find
The first item that passes the test.
returns one item
🗑️
filter
Every item that passes the test.
returns a smaller array
🔄
map
Transform each item into a new one.
returns same-size array
🥣
reduce
Boil the whole array down to one value.
returns one value
◆ Insight — the mental picture that makes these stick

map changes each thing (5 apples → 5 apple slices). filter keeps some things and throws the rest out (5 apples → the 3 red ones). reduce combines everything into one (5 apples → 1 smoothie). If you can answer "how many things come out?" you already know which method you want: same amount → map, fewer → filter, exactly one → reduce/find.

The inline arrow pattern

You can define a named test function and pass it in — but 90% of real code writes the function inline, right inside the method, using an implicit-return arrow. Both do the same thing:

two ways, same result
// verbose: named helper passed in
const isOdd = n => n % 2 !== 0
[1, 2, 3].find(isOdd)

// idiomatic: inline arrow, one line
[1, 2, 3].find(n => n % 2 !== 0)
Code anatomy — how an array method reads

See them run

One array, five methods. Edit anything and re-run to experiment.

array-methods.js
const nums = [4, 2, 3, 2, 7, 6]

// forEach — do something per item, returns nothing
nums.forEach(n => console.log("saw:", n))

// find — first item passing the test
console.log("first odd:", nums.find(n => n % 2 !== 0))

// filter — every item passing the test
console.log("no twos:", nums.filter(n => n !== 2))

// map — transform each item, same length out
console.log("plus one:", nums.map(n => n + 1))

// reduce — collapse to a single value (start at 1, multiply through)
console.log("product:", nums.reduce((total, n) => total * n, 1))
▲ Worth knowing — forEach returns undefined

Don't try to capture the result of forEach — there isn't one. const x = arr.forEach(...) makes x equal undefined, every time. Use forEach only for side-effects (logging, updating something external). If you want a new array back, you wanted map or filter.

◆ Insight — reduce is the secret power tool

The lecture calls reduce a "secret power," and it's right: reduce can technically do what map, filter and find do, because it can build up any shape of result — a number, a string, an array, an object. It's the hardest to read, so don't reach for it first. But when a problem is "combine this whole array into one thing" and nothing else fits, reduce is the answer. The two parameters are always in this order: (accumulator, currentItem) — the running total, then the item you're on.

console.log(arr.filter(n => n > 2))
console.log(arr.find(n => n > 2))

Watch the shapes: map gives back 4 items (same size), filter gives back 2 (fewer), find gives back a single value (3 — the first one over 2, not an array), and reduce sums everything to one number. Same array in, four different shapes out.

Modules

Splitting code across files. This is what lets a project grow past one giant file without losing your mind.

A module is just a file that keeps related code together and shares some of it with other files. Two systems exist in JavaScript:

  • CommonJS — the older style, uses require() and module.exports. You may have seen it in foundations.
  • ES Modules (ESM) — the modern style, uses import and export. This is what you'll use going forward.

Export what you make, import what you need

The idea: a "library" file exports functions, and other files import them. Here's the simplest working pair — a lib.mjs that offers up an add function, and an index.mjs that pulls it in and uses it.

lib.mjs
// define, then export
export const add = (a, b) => a + b
export const sub = (a, b) => a - b
index.mjs
// import by exact name, in braces
import { add, sub } from "./lib.mjs"

console.log(add(1, 2)) // 3
console.log(sub(7, 3)) // 4
Code anatomy — an import line

Named vs default exports

There are two flavours of export, and they change how you import:

Named exports — as many as you like

Put export in front of each thing. On the import side you list them in braces, and the names must match exactly.

named export → named import
// lib.mjs
export const add = (a, b) => a + b
export const sub = (a, b) => a - b

// index.mjs  —  names must match, wrapped in { }
import { add, sub } from "./lib.mjs"

Default export — exactly one per file

A file can have a single export default. On import there are no braces, and you can call it whatever you want — the name is yours to choose.

default export → free-choice import
// lib.mjs  —  only ONE default allowed per file
const add = (a, b) => a + b
export default add

// index.mjs  —  no braces; name is up to you
import anythingYouLike from "./lib.mjs"
✖ Gotcha — one default per file, no more

Try to export default add and export default sub in the same file and JavaScript throws: "a module cannot have multiple default exports." If you need to share several things, use named exports (or one default plus named ones). A common convention: default-export the "main" thing a file is about, and name-export the extras.

Import everything as one object

One more handy form: grab all the named exports at once as a single object with import * as lib. Then reach in with dots — lib.add, lib.sub. Nice because it's obvious where each function came from.

namespace import
import * as lib from "./lib.mjs"

console.log(lib.add(1, 2)) // 3
console.log(lib.sub(7, 3)) // 4
▲ Real-world note — you won't type .mjs for long

The lecture uses the .mjs extension as a temporary trick to force ESM to work in a bare node file. In actual projects you'll almost never see .mjs. Instead, a project's package.json has one line — "type": "module" — and from then on every ordinary .js file uses import/export automatically. So treat .mjs as training wheels: the import/export syntax is the real skill, the extension is scaffolding.

Recap & cheat sheet

The stuff to keep in your back pocket during the challenges.

Data types

  • 7 primitives: string, number, boolean, undefined, null, symbol, bigint
  • typeof null === "object" — the ancient bug. Just memorise it.
  • typeof [array] === "object" too. Only functions get "function".
  • NaN === NaN → false. Use Number.isNaN() to check for it.
  • Cast on purpose with Number() / String() / Boolean().
  • Default to === (value + type). Avoid == and its coercion surprises.
  • Primitives copy by value; objects/arrays share by reference.
  • const stops reassignment, not mutation — you can still edit an object's contents.

Functions

  • First-class: assign, pass, return — functions are values.
  • greeting refers to it; greeting() calls it. The parens matter.
  • Named / anonymous / arrow — same idea, three syntaxes.
  • Arrow: braces → explicit return; no braces → implicit return.
  • Braces without a return keyword = returns undefined (classic bug).
  • Higher-order = takes/returns functions. Closures = a function remembers its birthplace variables.

Array methods

  • forEach → undefined (side-effects only)
  • find → first matching item
  • filter → all matching items (smaller array)
  • map → same-size array, each item transformed
  • reduce → one value; args are (accumulator, current)
  • Ask "how many come out?" → same = map, fewer = filter, one = reduce/find

Modules

  • ESM uses import / export (CommonJS used require).
  • Named export → import { inBraces }, names must match exactly.
  • Default export → import with no braces, pick any name. One per file.
  • import * as lib grabs everything as one object → lib.add().
  • .mjs is a teaching crutch; real projects set "type": "module" in package.json.
