Arrays, and the one question that decides everything

Most array bugs come down to a single fork: did that method change my original array, or hand me back a new one? Get that straight and arrays stop fighting you.

This guide runs live, and it ends with your actual kata — all 12 functions, each with nudges you unlock step by step. The concepts above are ordered so that by the time you reach a challenge, you've already met the tool it needs.

$ npm test everything here maps to a function you're being asked to write.
01

Making & reading

Create an array, reach into it by index, and know what happens when you reach past the end.

The everyday way to make an array is a literal — square brackets with items inside. You read a single item by its index, counting from 0. Reaching for an index that doesn't exist doesn't crash — you just get undefined.

reading.js
const arr = ['a', 'b', 'c']

console.log(arr[0])       // first item — index starts at 0
console.log(arr[2])       // 'c'
console.log(arr.length)   // 3 — how many items
console.log(arr[10])      // undefined — NOT an error

There's also a constructor form, Array(n), that makes room for n slots. On its own that's just empty holes — but paired with .fill() it becomes a clean way to build an array of repeated values. Hover the pieces:

Code anatomy — build an array of repeats
Array(length).fill(item)

02

Rest & spread

Same three dots ..., two opposite jobs. This trips people up — so let's split them cleanly.

◆ Rest — gathers

In a function's parameters, ... collects all the arguments into a single array. Many things in → one array.

◆ Spread — unpacks

In an array literal or call, ... unpacks an existing array's items. One array out → many things.

Code anatomy — rest parameters (gathering)
function collect(...args) { return args }
Hover or tap a highlighted token above · this is challenge #2
—
Every part explains its own job.
rest-spread.js
// REST — gathers arguments into an array
function collect(...args) {
  return args
}
console.log(collect(1, 2, 3))     // [1, 2, 3]

// SPREAD — unpacks an array's items
const nums = [1, 2, 3]
console.log([...nums, 4])         // [1, 2, 3, 4]  (unpacked, then added 4)
console.log([0, ...nums])         // [0, 1, 2, 3]  (added 0, then unpacked)
console.log(Math.max(...nums))    // 3  (unpacked as separate arguments)
◆ Insight — spread is your copy tool

[...arr] makes a brand-new array with the same items — a copy at a new address. This is the move behind half your kata: whenever an exercise says "return a copy," spread is how you get one without touching the original. Straight out of the mutability guide.

03

Mutate vs copy

The spine of the whole topic. Some methods change the original array; others leave it alone and return a new one.

Fire methods at this array and watch two things: what the original looks like afterwards, and whether the method changed it or handed back something new.

✖ Why this matters for your kata

Nearly every kata function says "return a copy." That's a direct instruction to stay on the copies side of this table — map, filter, slice, spread. If you reach for push or splice on the array you were handed, you'll mutate the caller's original and (often) fail the test. When in doubt, build a new array.

?Predict the output
const a = [3, 1, 2]
const b = a.map(n => n + 10)
const c = a.filter(n => n > 1)
a.push(99)

console.log(b)

console.log(a)

[ 3, 1, 2, 99 ]
map and filter read a without changing it — so b and c are new arrays and a stayed [3,1,2] the whole time. Only push mutated it, adding 99 at the end.
04

Searching

Four methods that answer "is it in here?" and "which one(s)?" — and cover four of your kata functions.

MethodQuestion it answersGives back
includes(x)Is x in the array at all?true / false
indexOf(x)Where is x?its index, or -1 if absent
find(fn)The first item passing a test?that one item (or undefined)
filter(fn)Every item passing a test?a new array of matches
searching.js
const fruit = ['apple', 'pear', 'plum']

console.log(fruit.includes('pear'))   // true — clean yes/no
console.log(fruit.includes('kiwi'))   // false
console.log(fruit.indexOf('plum'))    // 2

const people = [{ name: 'Jo', age: 30 }, { name: 'Sam', age: 25 }]

console.log(people.find(p => p.age < 28))     // first match: { name: 'Sam', age: 25 }
console.log(people.filter(p => p.age >= 28))  // all matches: [{ name: 'Jo', age: 30 }]
◆ Insight — find vs filter is the same predicate

Notice find and filter take the identical test function — the only difference is find stops at the first match and hands back one item, while filter collects them all into a new array. That's the exact relationship between two of your kata functions (findOneByProperty vs findAll): write one, and the other is the same idea with the method swapped.

05

Transforming

Building a changed copy: map to swap items, filter to drop them, slice + spread to cut and rejoin.

These three cover the "return a copy with X changed" family of your kata. The trick most people miss: map and filter can hand your function the index as a second argument — which is how you target a specific position without mutating anything.

transforming.js
const arr = ['a', 'b', 'c', 'd']

// slice — copy a range [start, end)
console.log(arr.slice(1, 3))    // ['b', 'c']
console.log(arr.slice(2))       // ['c', 'd']  (from index 2 to the end)

// map with INDEX — swap the item at position 2, copy the rest
console.log(arr.map((el, i) => i === 2 ? 'X' : el))   // ['a','b','X','d']

// filter with INDEX — drop the item at position 1
console.log(arr.filter((el, i) => i !== 1))           // ['a','c','d']

For inserting (making the array longer), the classic idiom is to slice the array into two halves and spread them back around the new item. Hover it — this is the densest bit of syntax in the kata:

Code anatomy — insert without overwriting (slice + spread)
[...arr.slice(0, idx), item, ...arr.slice(idx)]

06

Arrays ↔ objects

Two built-ins turn objects into arrays-of-pairs and back — which is exactly what the zip/unzip challenges want.

arrays-objects.js
const obj = { foo: 1, bar: 2 }

console.log(Object.keys(obj))      // ['foo', 'bar']
console.log(Object.values(obj))    // [1, 2]
console.log(Object.entries(obj))   // [['foo', 1], ['bar', 2]]  — pairs!

// and back the other way:
console.log(Object.fromEntries([['x', 9], ['y', 8]]))   // { x: 9, y: 8 }
◆ Insight — pairs are the bridge

Object.entries gives you an array of [key, value] pairs; Object.fromEntries takes that shape and rebuilds an object. So "object → array of pairs" is one built-in, and "two arrays / pairs → object" is the reverse. Your unzipObject is almost literally one of these; zipObject is building pairs first, then either rebuilding with fromEntries or assembling with reduce.

▲ Handy — destructuring a pair

When you loop over pairs, you can unpack each one inline: arr.map(([key, value]) => …). The [key, value] on the left pulls the two slots out of each pair into named variables. Cleaner than pair[0] / pair[1], and it reads well in the zip/unzip functions.

How these work

Each challenge gives up to three nudges: concept → the method → the shape. They unlock one at a time on purpose — after each nudge, go back and try before opening the next. The final nudge points at the structure but stops short of the finished line: writing it is where the learning actually happens, so that part stays yours.

The two you flagged — hasItem and getItemAtIndex — get a firmer push since you're mid-fight with them.

✓ You've solved this — reference pattern
// makeArrayOfItem → an array `length` long, all `item` function makeArrayOfItem(item, length) { return Array(length).fill(item) }
This is your model. Array(length) makes the slots, .fill(item) drops the value into all of them. Clean and correct — keep it in mind for the fill-style problems.
✓ You've solved this — reference pattern
// makeArrayOfItems → an array of every argument passed in function makeArrayOfItems(...args) { return args }
Rest parameters in action — ...args gathers all arguments into one array, and you just return it. This is the gathering side of the ... from section 2.
// hasItem → true if `item` is in `arr` at least once, else false function hasItem(arr, item) {}
Concept
You want a straight yes/no. There's one array method whose entire job is to return true or false for "is this value in here?" — the kata's tip is pointing right at it. You met it in section 4.
The method
It's .includes(). arr.includes(item) already evaluates to exactly the boolean you need — no comparison or loop required.
The shape
The whole body is a single return of that expression. You're handing back the result of asking arr whether it includes item. One line. Write it and run npm test hasItem.
// getItemAtIndex → arr[idx] IF that index exists, // otherwise return a JavaScript Error object function getItemAtIndex(arr, idx) {}
Concept
Two possible outcomes means you need a condition first. Ask: "does this index actually exist in the array?" If yes, return the value; if no, return an Error. Remember from section 1 that a missing index gives undefined, and the array's .length tells you the valid range.
The tools
A valid index sits in 0 … arr.length - 1. So idx is out of range when idx >= arr.length (or idx < 0). To make an Error object, you use new Error('some message') — that's the JavaScript Error the exercise asks for.
The shape
Structure it as: if the index is out of range → return new Error(...); otherwise → return arr[idx]. You decide the exact condition and the message. Both branches must return. Test with npm test getItemAtIndex.
// replaceItemAtIndex → a COPY of `arr` with the element // at `idx` replaced with `item` function replaceItemAtIndex(arr, idx, item) {}
Concept
The word "copy" is the instruction — don't mutate arr. You're transforming one position and keeping the rest. Which section-3 method returns a new array the same length, and can see each item's index?
The method
map((el, i) => …). It hands you each element and its index, and returns a new array — so nothing gets mutated. You want to return item when the index matches, and the original el otherwise.
The shape
Inside the map, a ternary decides per element: is this index the target? → item : el. Assemble that into the map yourself. (Spread + assignment is a valid alternative route if you prefer.)
// insertItemAtIndex → a COPY of `arr` with `item` inserted // at `idx`, overwriting nothing (array gets LONGER) function insertItemAtIndex(arr, item, idx) {}
Concept
Longer, not replaced — so you're wedging item into a gap. Picture the array split in two at idx: everything before, then the new item, then everything from idx onward.
The method
slice gives you the two halves without mutating: arr.slice(0, idx) is the front, arr.slice(idx) is the back. Spread both into a new array literal with item between them. (This is the anatomy block in section 5.)
The shape
You have three pieces to combine in a new [ ]: the front slice (spread), the item, the back slice (spread). Your job is the order and where item sits. Look back at the section-5 anatomy if you want to check your assembly.
// deleteItemAtIndex → a COPY of `arr` without the element // at `idx` (array gets SHORTER) function deleteItemAtIndex(arr, idx) {}
Concept
Shorter by one, at a specific position. You want to keep every element except the one whose index is idx. "Keep everything that passes a test" should ring a bell.
The method
filter((el, i) => …) — filter also gives you the index. Keep the elements where the index is not the one you're deleting.
The shape
The test is a comparison on the index: keep when i !== idx. Drop that into a filter and return the result. (A slice + spread of the two halves also works if you'd rather.)
// deleteItem → an array with EVERY instance of `item` removed function deleteItem(arr, item) {}
Concept
Remove every copy of a value = keep everything that isn't that value. Same "keep what passes a test" tool as the last one — but now the test is about the value, not the index.
The method
filter. Keep each element where it is not equal to item.
The shape
The predicate is el !== item. One filter, returned. Notice how deleteItemAtIndex and deleteItem are the same method with a different test — index vs value.
// zipObject → an object from two arrays // ['foo','bar'], [1,2] → { foo: 1, bar: 2 } function zipObject(keys, values) {}
Concept
Each keys[i] pairs with the values[i] at the same position. So you're walking the indices and building up an object one key/value at a time.
Two routes
A) reduce over keys, using the index to grab the matching value, adding each pair onto an object you build up (start from {}). B) build the [key, value] pairs first with map, then hand them to Object.fromEntries (section 6).
The shape
Route B is shortest: keys.map((key, i) => [key, values[i]]) gives you the pairs — then wrap that in Object.fromEntries(...). Assemble it and confirm you see why the index lines the two arrays up.
// unzipObject → array of [key, value] pairs // { foo: 1, bar: 2 } → [['foo', 1], ['bar', 2]] function unzipObject(obj) {}
Concept
Object in, array-of-pairs out. That exact shape — [[key, value], …] — is what one specific built-in produces. You saw it in section 6.
The method
Object.entries(obj) returns precisely [['foo', 1], ['bar', 2]]. This one really is nearly a one-liner — return that. (If you want to earn it the long way, a loop over Object.keys building pairs also works.)
// findOneByProperty → the object in `arr` that has the // property AND value of `search` // [{a:1},{b:2,c:3}], {b:2} → {b:2,c:3} function findOneByProperty(arr, search) {}
Concept
"The object that has…" = the first match. Which section-4 method returns the first element passing a test? Your test per object: does it contain the same key/value that search holds?
The tools
find is the method. To write the test you need to know the key inside search. Since search is an object like {b: 2}, pull its key/value out — e.g. Object.entries(search)[0] gives you ['b', 2], which you can destructure into [key, value].
The shape
Get [key, value] from search, then arr.find(obj => obj[key] === value). That's the skeleton — decide how you extract the key/value and handle the comparison. (This assumes one property in search, which the examples use.)
// findAll → ALL objects in `arr` with the property // and value of `search` function findAll(arr, search) {}
Concept
This is findOneByProperty's twin — "all" instead of "the first." Same test, sibling method. If you cracked the last one, this is a one-word change.
The method
Swap find for filter. Identical [key, value] extraction, identical predicate obj[key] === value — filter just collects every match into a new array instead of stopping at the first.
◆ Before you refactor

Once they're green, the kata asks you to read your code back and clean it up — drop stray console.logs, remove duplication. Watch for the repeated [key, value] extraction in the last two functions; that's a natural spot to notice a shared pattern. Understanding why each one works is the actual goal here, not just the passing tests.

★

Recap

The array toolkit

  • Index from 0; a missing index is undefined, not an error. .length = count.
  • Array(n).fill(x) builds an array of repeats.
  • ... = rest (gathers args → array) in params, spread (unpacks array) in literals/calls.
  • Copy an array with [...arr] or slice().
  • MUTATE: push, pop, splice, sort, reverse. COPY: map, filter, slice, concat, spread.
  • "Return a copy" = stay on the copy side. Never push/splice the array you were handed.
  • Search: includes (yes/no), indexOf (where), find (first match), filter (all).
  • map/filter can take the index as a 2nd arg — that's how you target a position safely.
  • Objects ↔ arrays: Object.entries / Object.fromEntries; destructure pairs with [k, v].
  • find and filter = same test, one match vs all. So do findOneByProperty / findAll.
