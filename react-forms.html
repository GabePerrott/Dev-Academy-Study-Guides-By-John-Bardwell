Unit 2 — React Forms

Forms where state is the truth

A React form doesn't just collect data — it keeps every keystroke in state, so nothing reloads and nothing gets lost. This guide covers single-input forms, then the trickier multi-input ones, built on one idea you can watch happen: the value comes from state, and typing updates the state.

Part A

Single input forms

One field. Control its value with state, handle submit without reloading.

01

Why HTML forms break React

A plain HTML form reloads the page when you submit — and a reload wipes all your React state.

You built HTML forms in Foundations. They have an action and a method, and when you hit submit, the browser does its default thing: it reloads the page, sending your data up as a query string in the URL — localhost:3000/?color=red. That key color comes from the input's name.

That default is fine for old-school server pages, but it's poison for a React app. A reload throws away every piece of state — the transcript's demo had music playing and an animation running, and submitting killed both. Everything reset. The form even hid itself again. Terrible experience.

✖ The core conflict

React keeps your app's data in state, on the client, and never wants to reload. HTML forms want to reload and send data to a server. Those two instincts fight. The whole point of this unit is taking control of the form away from the browser's default so your React state survives — you keep the data on the client and decide yourself what happens on submit.

02

Controlled vs uncontrolled

Left to itself, a form controls itself (uncontrolled). We make it controlled — its value lives in React state, and we handle its events.

Two words you'll hear constantly:

Uncontrolled

The form runs on its own default behaviour — the browser holds the input's value, and submit reloads the page. You're not in charge of it.

Controlled

React holds the value in state, and you wire up event handlers (onChange, onSubmit) to control every step. You're in charge.

Making a form controlled comes down to two event handlers you'll meet — and they're well named, so they say what they do: handleChange (runs every time an input changes) and handleSubmit (runs when the form is submitted). You saw event handlers already with onClick in the React guide; these are the same idea, for forms.

◆ Insight — "controlled" means state is the single source of truth

In a controlled input, the input box doesn't hold its own value — it just displays whatever's in state. State is the truth; the input is a mirror. That's the same UI = f(state) idea from the React guide, applied to a text box: the box shows what state says, and the only way to change what's shown is to change state. Hold that picture — the next section makes it move.

value + onChange: the loop

Two attributes turn a plain input into a controlled one. Together they form a loop — and you need both halves.

A controlled input has two special attributes working as a pair:

✖ You need both halves — this trips everyone

value alone → a frozen, read-only box (state never changes, so the display never changes). onChange alone → an uncontrolled input React warns about. Only both together make the loop: state drives the display, and typing drives the state. If your input won't let you type, the missing onChange (or a setText that doesn't use event.target.value) is the first thing to check.

?Predict the state
const [text, setText] = useState('')

const handleChange = (event) => {
  setText(event.target.value)
}

// user types "cats" into <input value={text} onChange={handleChange} />
// what is `text` now?
text === 'cats'
Each keystroke fired handleChange, which set text to the input's current value. After typing "cats", state holds 'cats' — and because value={text}, the box shows it. State and screen stay in lockstep.

04

Handling submit

Stop the reload with preventDefault, then do what you actually want: add to a list, and clear the input.

Now submit. The form's default is to reload — so step one is to stop that with event.preventDefault(). Then you're free to do your own thing with the data:

Code anatomy — handleSubmit
const handleSubmit = (event) => { event.preventDefault() handleAddScare(text) setText('') }

See the difference preventDefault makes. Below is a mini "things that scare me" app with a bit of persistent state (the music toggle). Add a scare with the switch off, then on:

🔒 localhost:3000
    Turn the music on, type a scare, and submit — first with preventDefault on, then off. Watch what survives.

    With preventDefault on, the scare joins the list, the music keeps playing, the input clears — all your state survives. Turn it off, and submit reloads: the URL gains a ?scare= query, the music stops, the list resets. That's the uncontrolled default you're overriding.

    Two supporting pieces

    The submit handler above used handleAddScare. Two things make that work, and both echo earlier guides:

    Code anatomy — add to a list, and pass the function down
    // parent component: const handleAddScare = (newScare) => { setScares([...scares, newScare]) } <Form handleAddScare={handleAddScare} />
    Hover or tap a highlighted token above · spread to add immutably · functions can be props
    —
    Every part explains its own job.
    ◆ Insight — passing a function down is how a child talks back up

    Props usually flow data down (parent → child). But the form is the child, and the list lives in the parent — so how does the child add to it? The parent passes a function down as a prop. The child calls it, and the parent's state updates. This "callback prop" pattern is everywhere in React: data flows down, and functions flow down to let children send changes back up.

    ▲ Never mutate state — always make a new array

    [...scares, newScare] builds a brand-new array; it doesn't touch the old one. This matters because React decides whether to re-render by checking if the reference changed — the by-reference behaviour from the mutability guide. Push onto the existing array and React may not notice. Spread into a new one and it re-renders reliably. Same rule for objects, which Part B leans on.

    Part B

    Multi-input forms

    Many fields, collected into one object — with a single clever handler instead of one per field.

    05

    Many inputs, one handler

    A sign-up form has many fields. You could write a handleChange for each — or write one smart handler that works for all of them.

    Real forms collect several things at once: a name, a rating, an origin. You could give each input its own state and its own handler — and that's completely valid. But it's repetitive. The smarter move: collect everything into one object in state, and use one handleChange for every input.

    The trick is that the event knows which input fired it. Each input gets an id matching a key in your object, and the handler uses that id to update the right field:

    Code anatomy — one dynamic handleChange
    const handleChange = (event) => { setNewScare({ ...newScare, [event.target.id]: event.target.value }) }
    Hover or tap a highlighted token above · [id] picks the field · value fills it
    —
    Every part explains its own job.

    Watch it build. Type in any field — the single handler routes each keystroke to the right key, and the newScare object fills in live. The field you just touched flashes in the object:

    One handleChange → one object
    id="name"
    id="rating"
    id="origin"
    newScare (state)
    Type in a field — the handler will show which key it writes.
    ◆ Insight — the square brackets are the whole trick

    [event.target.id] is a computed property key — the square brackets tell JavaScript "don't use the literal word, use the value inside." So if event.target.id is "rating", you're setting the rating key. It's the same square-bracket idea from objects in Foundations, now doing real work: one line handles a form of any size. Miss the brackets and you'd create a key literally named "event.target.id" — a classic bug.

    ▲ Don't forget to spread the existing object

    The ...newScare at the top is essential. Updating state replaces it, so if you only set the one field, every other field would vanish on the next keystroke. Spreading copies the current values in first, then your one key overwrites just its own. Same immutable-update discipline as the array in Part A — make a new object, don't mutate the old.

    Checkpoint: why [event.target.id] in square brackets, not just event.target.id?
    06

    Building & submitting the object

    Wire each input's value back to the object, submit it into a list, and mind the array-vs-object trap the presenter hit live.

    To make the multi-input form fully controlled, each input also gets its value from the object — value={newScare.name}, value={newScare.rating}, and so on. Same loop as Part A, just one per field, all reading from the one object.

    Submit works exactly like before: preventDefault, add the object to your list state, clear the form. And a model keeps the object's shape honest:

    models/ratedScare.ts
    // a model in the models/ folder — separation of concerns
export interface RatedScare {
  name: string
  rating: string
  origin: string
}
// newScare state is typed as RatedScare — the shape the form fills in
    ✖ The live bug — array vs object

    The presenter's submit broke, and the cause is worth stealing as a lesson. Adding to the list needs a new array: setRatedScares([...ratedScares, newScare]) — square brackets. They accidentally used curly braces {...}, making an object instead of an array, and it broke. The fix came from reading the red squiggly line — TypeScript was pointing right at the type mismatch. Array to add to a list; the red underline tells you when you've slipped.

    ?Predict the object
    const newScare = { name: 'rats', rating: '', origin: '' }

// user types "8" in the input with id="rating"
setNewScare({ ...newScare, [event.target.id]: event.target.value })
    { name: 'rats', rating: '8', origin: '' }
    ...newScare copied all three fields, then [event.target.id] (which is 'rating') overwrote just that one with '8'. name and origin were preserved by the spread. Note rating is '8' — a string, because everything from an input is text.
    ▲ Input values are always strings

    Notice rating came out as '8', not 8. Everything typed into an input is text, even numbers — the same string-vs-number gotcha from the routing params. If you need to do maths with a rating, convert it with Number(newScare.rating). Design your model and checks with that in mind.

    ★

    Recap

    Why controlled forms

    • Plain HTML forms reload the page on submit (data → URL query), which wipes React state.
    • Uncontrolled = form runs on browser defaults. Controlled = React state holds the value, you handle the events.
    • Controlled means state is the single source of truth; the input just displays it (UI = f(state)).

    Single input

    • The loop: value={text} displays state · onChange={handleChange} updates it. Need both.
    • handleChange: setText(event.target.value) — event.target.value = what's typed.
    • handleSubmit: event.preventDefault() first (stop the reload), then your logic, then clear.
    • Add to a list immutably: setScares([...scares, newScare]) — new array, never mutate.
    • Pass a function down as a prop so the child form can update the parent's list.

    Multi input

    • Collect fields into one object in state; use one handleChange for all inputs.
    • Each input has an id matching an object key + value={newScare.key}.
    • The dynamic handler: setNewScare({ ...newScare, [event.target.id]: event.target.value }).
    • [event.target.id] = computed key (uses the id's value as the key). ...newScare keeps the other fields.
    • Add to the list with an array spread [...] — not {...}. Read the red squiggly.
    • Keep models in a models/ folder. Input values are always strings.
