Unit 4 · Express Server & JSON APIs

Now you're the one answering the requests

In Unit 3 you called APIs — you were the client, asking a server for data. This unit flips the table: you build the server. When a request arrives, your code decides what to send back.

Express is the tool that makes that easy. This guide walks the core arc — routes, the request object, JSON responses, and the testing loop that proves it all works.

request comes in → your route runs → response goes out
01

Client & server

A server is just a program that waits for requests and sends responses. It lives at an address and listens on a port.

A server is an application that runs somewhere, listens for incoming requests, and serves responses. A web server serves web pages and data. It sits at a network address and listens on a specific port — the numbered "door" where your app accepts connections (you'll see localhost:3000 constantly: address localhost, port 3000).

◆ Analogy — a restaurant kitchen

As the client in Unit 3, you were the customer placing orders. Now you're running the kitchen. Orders (requests) come in through a specific window (the port); each one names a dish (the route, like /birds); your job is to prepare the right thing and send it back out (the response). Express is the ticket rail that routes each order to the right station.

Your first server

A handful of lines stands up a working web server. Then one important split for testing later.

Code anatomy — a minimal Express server
import express from 'express' const server = express() server.get('/', (req, res) => { res.send('<h1>Hello world</h1>') })
Hover or tap a token · create the server · define routes · send responses
—
Each part explains its job.

The handbook splits this across two files, and the reason matters for testing later:

server.ts  +  index.ts
// server.ts — defines routes, exports the server (does NOT listen)
import express from 'express'
const server = express()
server.get('/', (req, res) => res.send('Hello world'))
export default server

// index.ts — imports the server and starts it listening
import server from './server.ts'
server.listen(3000, () => console.log('listening on 3000'))
▲ Why split server.ts from index.ts?

Because server.listen() starts a live server the moment the file runs — and you don't want a real server booting up during your tests. By keeping listen() in index.ts and exporting the plain server from server.ts, your tests can import the server and probe its routes without ever starting it. This split is the whole reason testing works cleanly (section 7).

03

Reading the request

Two ways data arrives in the URL: route params and query params. They land in different places on req.

The client sends data with the request. The two URL-based ways each have their own spot on the req object:

Code anatomy — route params vs query
server.get('/:org/:repo', ...) → req.params.org /webapps?person=Robin → req.query.person
Hover or tap a token · params identify a resource · query filters or configures
—
Each part explains its job.
◆ Which one to use

Rule of thumb from the handbook: route params (/:id) for which thing — the identity of a resource. Query (?sort=name) for how — filtering, sorting, options. REST web APIs lean heavily on route params, so /birds/42 is preferred over /birds?id=42.

04

JSON APIs

A JSON API accepts and responds with JSON. Two small additions to what you already know.

Exposing a web API works exactly like other routes — the difference is you respond with JSON using res.json(), which serialises a plain JavaScript object for you:

json-route.ts
server.get('/:id', (req, res) => {
  const widget = { id: req.params.id, name: 'Best widget' }
  res.json(widget)   // serialises the object to JSON automatically
})

To receive JSON in a POST or PUT body, you switch on one piece of middleware — a function that processes every request before your route sees it:

receiving-json.ts
const server = express()
server.use(express.json())   // middleware: parse JSON bodies onto req.body

server.post('/widget', (req, res) => {
  const newWidget = req.body   // now available thanks to express.json()
  // ...save it, then respond
})
▲ No express.json() → req.body is undefined

The single most common "why is my POST body empty?" bug. Without server.use(express.json()) (or express.urlencoded() for HTML form posts), Express never parses the body and req.body comes back undefined. The route looks right; the middleware is missing.

06

Static files & Router

Two tools that keep a growing server tidy — serving files automatically, and splitting routes into modules.

Serving static files

HTML, CSS, images, client-side JS — files that go out unchanged. Rather than a route per file, point Express at a folder and it serves everything inside automatically:

static.ts
import * as Path from 'node:path'
const publicPath = Path.resolve('./public')
server.use(express.static(publicPath))
// public/styles/main.css  →  http://localhost:3000/styles/main.css
// note: 'public' is NOT part of the URL

Express Router — modular routes

As routes pile up, server.ts gets crowded. express.Router() lets you move a group of related routes into their own file and mount them under a prefix:

server.ts  +  bird-routes.ts
// server.ts — mount the router under /birds
server.use('/birds', birdRoutes)

// bird-routes.ts — note: no 'birds' in here, the prefix is applied above
const router = express.Router()
router.get('/', ...)      // actually handles GET /birds
router.get('/:id', ...)   // actually handles GET /birds/:id
export default router
◆ The prefix is applied once, at mount

The thing that trips people: inside bird-routes.ts you write '/' and '/:id', not '/birds'. The /birds prefix was set once by server.use('/birds', birdRoutes). Writing /birds again inside the router would make the real path /birds/birds.

07

Testing with Supertest

The assessment-critical part. Supertest sends fake requests to your exported server and checks the response — no browser, no live server.

Remember the split from section 2? Because server.ts exports the server without calling listen(), your test can import it and fire requests straight at it with Supertest. The shape is Arrange / Act / Assert:

Code anatomy — a route test
import request from 'supertest' import server from '../server.ts' test('/example returns WOMBAT', async () => { const res = await request(server).get('/example') expect(res.text).toBe('WOMBAT') })
Hover or tap a token · import server · await a request through it · assert on the response
—
Each part explains its job.

The three things you check, depending on the route:

Assert onIsUse for
res.statusthe HTTP code200 OK, 201 Created, 404 Not Found
res.textthe raw body textHTML routes, plain strings
res.bodythe parsed JSONAPI routes returning objects/arrays

Testing a POST route is the same, plus sending data — .type('form') or JSON, then .send(data):

post.test.ts
const res = await request(server)
  .post('/')
  .type('form')
  .send({ name: 'flargle' })
expect(res.text).toContain('flargle')
✖ Always await before you assert

The request returns a promise. Assert too early — before the await resolves — and you're checking an empty/pending response, giving confusing failures. This is the same async lesson from Async & Promises, now on the server side. These route tests span more than one unit of code (server + routing), so they're really integration tests, not unit tests.

★

Recap

The server

  • A server listens for requests, sends responses, at an address + port (localhost:3000).
  • server.get('/path', (req, res) => ...) defines a route; res.send / res.json reply.
  • Split server.ts (routes, exported) from index.ts (listen()) so tests can run without a live server.

Reading data & JSON

  • Route params /:id → req.params (which resource). Query ?x= → req.query (filters).
  • POST/PUT body → req.body, but only with server.use(express.json()) middleware.
  • res.json(obj) serialises an object to JSON for you.

Organising & testing

  • express.static(folder) serves files automatically; express.Router() splits routes into modules.
  • Use methods correctly: GET reads (no side effects), POST saves.
  • Supertest: await request(server).get('/x'), then assert res.status / res.text / res.body.
  • Always await the request before asserting — these are integration tests.
